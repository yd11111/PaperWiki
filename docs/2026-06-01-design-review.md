## 4. 是否满足核心职责：筛 / 懂 / 连

### 4.1 筛：是否帮助减少无效注意力消耗

**评价：**
- 是否满足：**是**
- 优点：
  - 多入口(每日推荐 + 外部导入 + inbox)
  - 优先级机制(LLM 打分排序)
  - 低成本初筛(卡片自动生成,零人工成本)
  - 升级路径(inbox → card → enhanced-card → deep → repro,逐步加码)
  - "默认不升级"原则防止过度投入
- 缺口：
  - 未显式记录"为什么不读"。每日推荐中被跳过的论文没有留痕,无法事后追溯"当时为什么没选这篇"。这对于回溯自己的注意力决策有一定价值,但不是必须。
- 风险：无显著风险。
- 建议：可考虑在 DailyPapers 中对未选论文保留卡片(当前已有),不需额外机制。缺口很小,不建议为此增加设计复杂度。

---

### 4.2 懂：是否支持从"知道存在"到"真正理解"

**评价：**
- 是否满足：**是**
- 优点：
  - 四层深度分级(card/enhanced-card/deep/repro)
  - 精读产出原则明确要求"机制理解而非更长摘要"
  - 线索层(card/enhanced-card)和理解层(deep/repro)有明确边界
  - 人工审核(status: draft → reviewed)保证理解质量
  - KB 上下文让新论文自动获得已有认知背景,辅助理解
- 缺口：
  - "机制理解"目前是一条原则声明,但没有定义什么样的笔记内容结构能确保这一点(如:是否要求"为什么 work"必须作为独立小节)。这属于模板层面问题,不在本次审阅范围,但需要在模板设计时兑现。
- 风险：如果模板不强制"为什么 work"这一节,agent 仍可能回退到高级摘要模式。
- 建议：在 P1 实现精读模板时,确保有独立的"机制解释"小节(不只是方法描述)。

---

### 4.3 连：是否能把单篇输入接入知识网络

**评价：**
- 是否满足：**是**
- 优点：
  - 四类稳定实体层(概念/模型/任务/数据集)
  - 不只按论文组织,实体页按认知结构组织
  - 反向更新机制(每次精读自动更新相关实体页)
  - MOC 按研究主题导航
  - KB 上下文让旧知识主动参与新知识理解(复利核心)
- 缺口：
  - 实体页之间的关系类型未定义。当前只有 `related_concepts` 和 `supersedes/superseded_by`,但没有定义如"X 是 Y 的特例""X 改进了 Y""X 和 Y 互为竞品"这类语义关系。这在早期不是问题,但 50+ 概念时会影响导航精度。
- 风险：中期(100+ 实体页)后,扁平的 `related_concepts` 列表区分不出关系强度和类型。
- 建议：作为 P5 增强考虑,不阻碍当前设计。

**评价：**
- 是否满足：**是**

  - 两级 lint(基础健康 + 高级认知)

## 9. 关键漏设计

### 漏设计清单

#### 1. 未声明 Git 作为版本控制基础设施

- **为什么是漏设计:** 概念页会被反复更新。没有版本控制,误更新不可回滚,无法做 blame("这句话是哪次 ingest 加的"),无法做 diff("这次确认和上次确认之间改了什么")。Karpathy 原设计明确说"wiki 就是一个 git repo"。
- **会导致什么后果:** 误更新污染概念页 → 无法恢复 → 可信层受损 → 信任下降。
- **建议:** 在架构总览中声明:vault = git repo,每次 ingest 操作自动 commit,commit message 包含操作类型和涉及页面。审核确认也产生 commit。

#### 2. 实体页缺少生命周期定义

- **为什么是漏设计:** 概念页从创建到成熟到可能需要合并/拆分/退役,没有定义这个过程。`aliases` 和 `lint 检测近义` 只是缓解,不是管理机制。
- **会导致什么后果:** 中期(80+ 概念)出现重叠概念页(如"Neural Codec" vs "Audio Codec" vs "Speech Codec"),没有合并流程;旧概念(如某个被完全淘汰的方法)没有退役机制,MOC 越来越长。
- **建议:** 定义实体页状态:`active | deprecated | merged-into:[[Target]]`。合并操作:旧页保留为 redirect(frontmatter 标记 merged-into),内容移到目标页。退役:标记 deprecated,从 MOC 活跃区移到"历史"区。不需要立即实现,但顶层应定义。

#### 3. 未定义审核确认的具体仪式/节奏

- **为什么是漏设计:** "批量确认"是概念,但何时做、怎么做、做多久没有定义。如果没有固定节奏,审核就不会发生(因为不紧急)。
- **会导致什么后果:** pending-review 长期积压 → 可信层长期空虚 → KB 检索无可信数据可读 → 系统复利无法启动。
- **建议:** 建议定义一个轻量级审核仪式(不是系统强制,是建议):如"每周花 30 分钟集中审核 pending-review 页面"。可以在 lint 周报中附带"本周待审清单"来触发。

## 10. 可能的设计错误

### 设计错误/风险点

#### 1. pending-review 状态频繁震荡 — 可信层可能长期空虚 (严重度: 高)

- **错误/风险是什么:**
  当前设计:每次精读 ingest 的反向更新 → 概念页 status 变为 pending-review。
  问题:一个活跃概念(如"Flow Matching")可能每周被 2-3 篇新论文引用 → 每周被更新 2-3 次 → 每次都变回 pending-review → 你周末刚确认完,下周又变回 pending → 这个概念页几乎永远不在 confirmed 状态。
  结果:KB 检索该概念时始终标注"未确认" → 最重要的概念反而得不到可信背景。

- **为什么危险:**
  高频活跃概念恰好是你最需要 KB 背景的概念。如果可信层总是排除它们,系统的复利效果被严重削弱。

- **是否需要立刻修正:** **是。这是当前设计最大的结构性问题。**

- **修正建议:**
  区分"追加更新"和"实质修改":
  - **追加更新**(如往 key_papers 列表加一篇、在正文末尾追加一句新贡献):不改变 status,保持 confirmed。这类更新风险极低,不值得打断可信状态。
  - **实质修改**(如修改概念定义、重写核心描述、改变 related_concepts):status → pending-review,需要你确认。

  判断标准:如果更新只是"往已有结构中加条目",不触发 pending-review;如果更新"改变了页面的核心语义",触发 pending-review。

#### 2. KB 检索的搜索召回率未被保证 (严重度: 中)

- **错误/风险是什么:**
  当前搜索依赖 tags + aliases 精确匹配。但论文可能用新术语描述已有概念(如"rectified flow" vs "flow matching"),如果 aliases 没有覆盖到,就会漏掉最相关的概念页。

- **为什么危险:**
  KB 背景漏掉关键概念 → 创新判断不准确("误以为新"或"误以为旧") → 知识库的定位价值打折。

- **是否需要立刻修正:** 否。这是 P3 实现时需要关注的,顶层设计可以先声明"aliases 需要持续维护"。但认知到这个风险很重要。

- **缓解建议:**
  - 每次 KB 检索后,log 记录匹配了哪些页面
  - 你审核精读笔记时,如果发现 KB 背景遗漏了明显相关的概念,手动补充 alias
  - 长期:考虑引入模糊匹配或 embedding-based 检索(P5+)

## 11. 可能的过度设计

### 过度设计项

#### 1. 加强卡片(enhanced-card)作为独立层级 (轻微)

- **为什么属于过度设计:** 卡片和加强卡片的界限模糊。加强卡片提供"方法概述+关键结果",但这些信息是否真的帮你决定"要不要精读"?还是你看了标题和 abstract 就已经能判断了?如果后者,加强卡片只是一个"不想精读但觉得只有卡片太少"的心理安慰层。
- **是否值得保留:** 保留为"可用能力",但观察实际使用频率。
- **建议:** 不删除,但标注为"试运行"。2-3 周后如果你发现自己直接跳过 enhanced-card 直接精读,说明这层多余,可简化为三层。

#### 2. _inbox/ 作为独立目录 (轻微)

- **为什么属于过度设计:** 对于 TTS 研究者,论文来源相对集中(arXiv daily + 同行推荐)。"先收着暂不判断"的场景确实存在,但频率可能不高——大部分时候你要么在 DailyPapers 里选读,要么直接丢进来精读。
- **是否值得保留:** 保留。inbox 的实现成本极低(就一个目录 + 最简 frontmatter),即使用得少也不碍事。
- **建议:** 保留,不需改动。如果 3 个月后 inbox 里常年只有 0-2 个条目,可以考虑去掉。

#### 3. 六条系统原则的条数 (极轻微)

- **为什么属于过度设计:** 六条原则对于一个单人系统来说略多。但它们的主要受众是 AI agent(约束 agent 行为),不是你自己需要背诵。
- **是否值得保留:** 保留。作为 AGENTS.md 中的规则,它们的认知成本由 agent 承担,不由你承担。
- **建议:** 无需改动。
