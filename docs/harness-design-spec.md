# Harness 设计规范

> 本文是一份通用的 Harness Engineering 指导规范，适用于任何 AI agent 驱动的知识生产系统。
> PaperWiki 的具体系统设计以本规范为锚点。
>
> 版本: v1.0
> 日期: 2026-06-04
> 来源: OpenAI Codex 实践 + Anthropic/Carlini 并行 agent + Mitchell Hashimoto Ghostty + Martin Fowler 框架 + 知乎深度分析

---

## 0.1 核心定理

> **Agent 的产出质量不取决于 agent 的智力，取决于围绕 agent 的约束和反馈机制的质量。**

推论：
- 当 agent 犯错时，正确反应不是"让 agent 更小心"，而是"缺了什么约束/反馈？"
- 如果一条规则只写在文档里靠 agent "理解"，它就会被违反
- 模型会变，harness 不变——投资 harness 的 ROI 高于投资 prompt

---

## 0.2 三层治理架构

任何 AI 知识生产系统都应有三层治理：

| 层 | 类比 | 特征 | 变更频率 |
|---|------|------|---------|
| **宪法层** | 宪法 | 从使用场景推导的原则，回答"对用户有什么用" | 极少变动 |
| **法律层** | 法律 | 原则的具体检查项，可机械执行，回答"怎么验证" | 每轮模式分析后更新 |
| **判例层** | 判例 | 单次审阅发现，回答"具体哪里出了问题" | 每次审阅积累 |

### 三层关系规则

- **宪法不依赖法律** — 即使所有检查项都通过，原则判断仍可以不满足（说明检查项有 gap）
- **法律可以溯源到宪法** — 每条检查项必须标注它服务哪条原则
- **判例反哺法律** — 高频判例 → 提炼为新检查项 → 法律层演进
- **宪法层极少变动** — 只有系统目标本身改变时才修改

### 关键信号

| 信号 | 含义 |
|------|------|
| 检查项全通过但原则不满足 | 检查项有 gap，需要补充新检查项 |
| 原则满足但检查项 fail | 格式问题，不影响实质，severity = low |
| 同一检查项反复 fail | 上游规则缺失或不够强，需要加固 |
| 出现检查项词汇表外的新问题 | 词汇表需要扩展，可能需要新检查项 |

## 0.3 双向反压模型

```
上游反压 (Feedforward)              下游反压 (Feedback)
──────────────────────              ──────────────────────
模板 / 规则 / skill                  审阅 agent / linter / 验证脚本
约束 agent 的生成行为                检查 agent 的产出质量
在 agent 动手之前生效                在 agent 完成之后生效
降低出错概率                         发现逃逸的错误
```

### 设计原则

- **上游优先**：能通过规则预防的问题，不要等下游审阅发现
- **下游兜底**：上游规则不可能覆盖所有情况，下游审阅是安全网
- **闭环连接**：下游发现的高频问题 → 分析根因 → 转化为上游规则

### Fowler 的 2x2 矩阵

| | 计算性 (确定性, 快) | 推理性 (语义, 慢) |
|---|---|---|
| **上游 (Feedforward)** | 模板预设字段/结构 | AGENTS.md / skill 规则 |
| **下游 (Feedback)** | lint 脚本 / 格式检查 | 审阅 agent |

优先投资左列（计算性），因为确定性高、成本低。右列（推理性）作为补充。

## 0.4 约束的机械化执行原则

> **如果一条约束不能被机械化验证，agent 就会偏离。**

### 约束的三种形态（按强度递增）

| 形态 | 示例 | 执行方式 | 可靠度 |
|------|------|---------|-------|
| **文档约束** | "请注意年份要一致" | 靠 agent 读文档后自觉遵守 | 低 |
| **模板约束** | 模板中预设字段/结构 | agent 填充模板，结构错误概率低 | 中 |
| **脚本约束** | bash/python 验证脚本 | 确定性检查，pass/fail | 高 |

### 升级路径

发现某条文档约束反复被违反 → 先尝试转为模板约束 → 仍不够则升级为脚本约束。

### 关键实践

- 验证脚本的错误信息应该是 **agent 可读的修复指令**，不只是 "violation detected"
- 错误消息本身就是一个 prompt，使 agent 能自我修正
- 禁用 inline-disable（如 `// eslint-disable-next-line`），否则 agent 会抑制报错而非修复
- 所有约束设为 `error`，不用 `warn` — 对 agent 来说 warn 等于不存在

## 0.5 Agent 分离原则

| 原则 | 说明 |
|------|------|
| **生成者不审自己** | 产出 agent 和审阅 agent 必须是独立 session |
| **最小权限** | 每个 agent 只持有完成其任务所需的最小工具集 |
| **最小上下文** | 每个 agent 只接收与当前任务相关的规则和文件，不加载全量规则 |
| **角色不混合** | 一个 agent 不同时承担生成和审阅职责 |

### Agent 角色分类（参考 Carlini 实践）

| 角色 | 权限 | 职责 |
|------|------|------|
| Research Agent | read-only | 搜索、检索、信息收集 |
| Planning Agent | read-only | 分析、规划、方案设计 |
| Execution Agent | scoped read-write | 按规则生产内容 |
| Review Agent | read-only + flagging | 审阅产出质量 |
| Cleanup Agent | scoped read-write | 熵管理、一致性修复 |

## 0.6 闭环演进机制

闭环是 harness 与静态规则系统的本质区别。

### 四步闭环

```
① 审阅产出判例 (单次发现)
   ↓
② 判例积累 → 模式分析 (统计高频问题)
   ↓
③ 根因归属 (问题出在哪一层？)
   - 上游规则缺失 → 补充规则 (AGENTS.md / skill)
   - 检查项缺失 → 补充检查项 (法律层演进)
   - 新问题类型 → 扩展问题词汇表
   - 模板不足 → 改进模板
   ↓
④ 规则更新 → 下次生成/审阅自动应用新规则
```

### 关键约束

- 步骤③的根因归属和规则修改建议由 agent 产出，但**实际修改由人确认后执行**
- 每次规则更新必须记录在检查项的更新日志中（可追溯）
- 闭环周期由审阅积累量驱动（如每 N 次审阅触发一次模式分析），不是固定时间

### 闭环质量信号

| 信号 | 好 | 坏 |
|------|---|---|
| 同类问题出现频率 | 递减（规则生效） | 持平或递增（规则无效） |
| 新问题类型出现率 | 偶尔出现（系统在扩展） | 从不出现（审阅覆盖不足？） |
| 规则更新频率 | 稳定（系统在收敛） | 过高（规则设计有问题） |

## 0.7 上下文管理原则

来自 Harness 研究的核心发现：上下文利用率超过约 40% 后，质量急剧下降。

### 分层上下文架构

| 层 | 内容 | 加载时机 | 大小 |
|---|------|---------|------|
| **Tier 1** | 系统总纲（AGENTS.md 级） | 每个 session 自动加载 | 小（< 2K tokens） |
| **Tier 2** | 任务专用规则（skill + checklist） | agent 执行特定任务时加载 | 中（2-5K tokens） |
| **Tier 3** | 知识库内容（实体页、已有笔记） | agent 按需检索 | 大（按需取 Top N） |

### 原则

- **Tier 1 是目录，不是百科全书** — 指向具体规则文件的位置，不内联规则内容
- 每个 agent 只加载与自己角色相关的 Tier 2 规则
- Tier 3 通过检索获取，设上限（如 Top 6 实体页）
- AGENTS.md 应控制在 ~100 行以内，超出部分拆到专用文档

### OpenAI 的教训

> "一个巨大的 AGENTS.md 会失败，因为：上下文是稀缺资源、太多指导等于没有指导、它会立刻腐烂、它无法被机械化验证。"

## 0.8 熵管理原则

AI 生成的内容会累积特有的熵（冗余、漂移、不一致）。需要定期清理。

### 设计原则

- **清理吞吐量应与生成吞吐量成比例** — 生成越快，清理频率越高
- **清理 agent 的权限是 scoped write（只修不加）** — 不能引入新内容
- **清理范围有确定性边界** — 如"所有 3 月未更新的概念页"，不做开放式重组

### 熵的四种形态

| 熵类型 | 表现 | 检测方式 |
|--------|------|---------|
| 冗余 | 重复条目、语义重叠的概念页 | 去重检查 |
| 漂移 | 文档说一套，实际做另一套 | 规则 vs 实际对照 |
| 不一致 | 不同页面对同一概念描述矛盾 | 交叉引用检查 |
| 过时 | 标记的 SOTA 已被超越、3 月未更新 | 时间戳检查 |

## 0.9 失败处理原则

> **失败降级，不阻断 pipeline。**

- 上游约束失败（如模板不匹配）→ 记录 + 用最近的合理默认值继续
- 下游审阅失败（如审阅 agent 超时）→ 标注"未审阅" + 跳过，不阻断后续步骤
- 闭环失败（如模式分析无法归因）→ 记录为"未归因问题" + 留给人工处理
- 关键原则：**失败信息必须被记录**，即使流程继续，问题不能被静默吞掉

## 0.10 度量与可观测性

一个 harness 至少需要跟踪以下指标：

| 指标 | 定义 | 用途 |
|------|------|------|
| **问题逃逸率** | 审阅未发现但用户发现的问题 / 总问题数 | 衡量审阅覆盖度 |
| **规则有效率** | 某条规则加入后该类问题下降比例 | 衡量上游反压效果 |
| **闭环周期** | 从问题发现到规则更新的平均间隔 | 衡量演进速度 |
| **审阅积压** | 待审阅产出数量 | 衡量产出/审阅吞吐平衡 |

## 0.11 演进原则

> **基于现有系统演进，不从头搭建。**

### 理由

1. **Harness 的核心生长方式是"从失败中长出规则"** — 已有的审阅报告、用户反馈、历史问题是 harness 最宝贵的原料。重建 = 丢掉判例
2. **成熟度模型是分级爬升，不是跳级** — Level 1 → 2 → 3，每一级在上一级基础上叠加能力
3. **避免过度设计** — "If you over-engineer the control flow, the next model update will break your system."（Augment Code）

### Harness 成熟度模型

| Level | 特征 | 人的角色 |
|-------|------|---------|
| Level 0 | 直接 prompt，无结构化约束 | 手动编写 + 偶尔 AI 辅助 |
| Level 1 | AGENTS.md + 基础 linter + 手动测试 | 主要编写，AI 辅助 |
| Level 2 | CI 集成 + 自动化测试 + 进度追踪 | 规划+审阅为主，部分 AI 执行 |
| Level 3 | 多 agent 角色分离 + 分层上下文 + 持久化记忆 | 环境设计 + 管理 |
| Level 4 | 无人值守并行 + 自动熵管理 + 自修复 | 架构师 + 质量守门人 |

### 演进策略

1. **识别现有系统的缺口**（对照本规范逐条检查）
2. **按优先级排序**（上游反压缺口 > 下游审阅缺口 > 闭环机制缺口）
3. **逐个补上，每次只改一个层面**
4. **改完验证效果再改下一个**
