# PaperWiki 评估体系设计

> 原则是宪法,检查项是法律,案例是判例法。

---

## 一、三层结构

```
┌─────────────────────────────────────────┐
│           原则层 (宪法)                  │
│  5 条评估原则,极少变动                   │
│  定义"好的笔记应该让用户得到什么"         │
└─────────────┬───────────────────────────┘
              │ 指导派生
┌─────────────▼───────────────────────────┐
│           检查项层 (法律)                 │
│  具体的、可执行的检查条目                 │
│  随系统架构演进而更新                     │
└─────────────┬───────────────────────────┘
              │ 产出积累
┌─────────────▼───────────────────────────┐
│           案例层 (判例法)                 │
│  每次审阅的具体发现                       │
│  存放在 _review/*.yml                    │
└─────────────────────────────────────────┘
```

---

## 二、5 条原则 (稳定锚点)

从用户使用场景推导,不从文档属性推导:

| 原则 | 使用场景 | 核心问题 |
|------|----------|----------|
| **可复述** | 3 个月后回来看这篇笔记 | 读完笔记(不看原文),能向同事解释这篇为什么 work 吗? |
| **可信赖** | 引用笔记中的数据写报告 | 笔记里的每个事实,你敢直接写进自己的报告吗? |
| **可区分** | 决定是否复现某个方法 | 哪些是论文用实验证明的,哪些是 agent 的推测?边界清楚吗? |
| **可定位** | 读新论文时 KB 背景提供定位 | 这篇在领域中的位置清楚吗?和已有知识的关系明确吗? |
| **不污染** | 笔记信息流入概念页 | 这些信息进入概念页后,会让未来的 KB 背景更好还是更差? |

**这 5 条原则不随系统版本变化。** 它们锚定的是用户需求,不是文档格式。

---

## 三、检查项 (动态演进)

检查项是原则的当前实例化。它们**会过时、会被替换、会被细化**——这是正常的。

### 当前检查项 (v1, 基于系统现状)

**原则: 可复述**
- [ ] "方法:它怎么 work" 节是否包含因果解释(WHY),而非仅组件罗列(WHAT)
- [ ] 每个关键设计选择是否回答了"为什么选这个"

**原则: 可信赖**
- [ ] 数字型 claim 旁是否有 [§X.X]/[Table N] 标注(覆盖率)
- [ ] 指标名是否正确(CER/WER/MOS/SIM 不混淆)

**原则: 可区分**
- [ ] 因果解释是否标注了 [论文原文] 或 [agent 解读]
- [ ] 是否存在把推断写成断言的句子(缺少"作者认为/实验显示"限定词)

**原则: 可定位**
- [ ] KB 背景节是否有具体谱系定位(不是"与已有工作相关")
- [ ] 速查卡片 5 字段是否都有实质内容
- [ ] frontmatter concepts/models/tasks 挂接是否完整

**原则: 不污染**
- [ ] 新建概念页是否满足准入规则
- [ ] 反向更新内容中是否有 factual-error 或 overclaim

## 四、完整循环 (系统怎么转起来)

```
┌──────────────────────────────────────────────────────┐
│                                                      │
│  ① 工作 Agent 精读论文,产出笔记草稿                  │
│                                                      │
└──────────────┬───────────────────────────────────────┘
               ↓
┌──────────────▼───────────────────────────────────────┐
│                                                      │
│  ② 审阅 Agent 用当前检查项审阅草稿                    │
│     底层: 机械检查(标注率、指标名、frontmatter)        │
│     上层: 原则判断(可复述?可信赖?可区分?)             │
│     产出: _review/xxx-review.yml + 笔记 callout       │
│                                                      │
└──────────────┬───────────────────────────────────────┘
               ↓
┌──────────────▼───────────────────────────────────────┐
│                                                      │
│  ③ 用户看审阅结果,决定:                               │
│     - pass → 反向更新                                 │
│     - 有问题 → 修正后反向更新                          │
│     - 审阅本身有问题(误报/漏报) → 也是信号            │
│                                                      │
└──────────────┬───────────────────────────────────────┘
               ↓
┌──────────────▼───────────────────────────────────────┐
│                                                      │
│  ④ 案例积累 (每篇审阅结果存入 _review/)               │
│                                                      │
└──────────────┬───────────────────────────────────────┘
               ↓ 每 5-10 篇触发
┌──────────────▼───────────────────────────────────────┐
│                                                      │
│  ⑤ 模式分析: 读取所有案例,输入三个东西:               │
│     A. 5 条原则 (不变的锚点)                          │
│     B. 当前检查项 (正在用的法律)                      │
│     C. 积累的案例 (发现了什么问题)                    │
│                                                      │
│     回答三个问题:                                     │
│     1. 哪些检查项已经不再发现问题了?                  │
│        → 工作 Agent 已经学会了 → 可以弱化/移除        │
│     2. 哪些问题反复出现但当前检查项没覆盖?            │
│        → 需要新增检查项                               │
│     3. 检查项和原则之间有没有 gap?                    │
│        → 原则要求的但检查项没查的 → 补上               │
│                                                      │
│     产出:                                             │
│     - 更新后的检查项 (review-checklist.md)             │
│     - 工作 Agent 规则改进 (AGENTS.md / skill / 模板)  │
│                                                      │
└──────────────┬───────────────────────────────────────┘
               ↓
┌──────────────▼───────────────────────────────────────┐
│                                                      │
│  ⑥ 系统升级:                                         │
│     - 检查项更新 → 下一轮审阅用新标准                  │
│     - 工作规则更新 → 下一轮产出质量提升                │
│     → 回到 ①                                         │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**循环的关键:**

- **①→②**: 工作 Agent 和审阅 Agent 是独立的(GAN 的 G 和 D)
- **③**: 用户是最终裁判(不是审阅 Agent 说了算)
- **④→⑤**: 案例积累到一定量才分析(不是每次都改规则)
- **⑤**: 模式分析的输入是三个东西(原则+检查项+案例),不是只看案例
- **⑤→⑥**: 检查项和工作规则**同时更新**(双向进化,不是只改一边)
- **原则始终不变**: 它是循环的锚点,防止系统在迭代中漂移

---

## 五、防漂移机制

没有锚点的迭代会漂移。5 条原则是防漂移的锚:

| 漂移风险 | 原则怎么纠偏 |
|---|---|
| 检查项越加越多,审阅变成走形式 | 用原则重新审视:"这个检查项真的帮用户判断可信赖吗?"不帮→删 |
| 工作 Agent 学会了应付检查项但笔记实际质量没提升 | 用原则直接问:"读完这篇笔记,我能复述吗?"不能→检查项没抓到真问题→改检查项 |
| 审阅 Agent 总是 pass,失去价值 | 用原则抽查一篇:"信息进概念页后会让 KB 更好吗?"不会→审阅标准太松→加严 |

## 六、与系统其他模块的关系

```
评估体系 ──── 原则层: 稳定锚点,写在本文档
   │
   ├── 检查项层: 写在 _templates/review-checklist.md (动态更新)
   │
   ├── 审阅执行: paperwiki-reviewer skill (用检查项审阅)
   │
   ├── 案例积累: _review/*.yml (每次审阅产出)
   │
   ├── 模式分析: 每 5-10 篇手动触发 → _review/pattern-analysis-*.md
   │
   ├── 工作规则: AGENTS.md / paperwiki-reader skill / _templates/ (被更新)
   │
   └── 用户: 最终裁判 + 确认系统升级
```
