## 一、一个核心问题: 为什么 Token 设计在"辗转反复"?

### 1.1 TTS 的三个根本目标

任何 TTS 系统最终都在优化三个目标:

```
              快 (推理速度/延迟)
              △
             / \
            /   \
           /     \
          /  TTS  \
         /  系统   \
        /___________\
   稳                 好
(发音正确性)      (表现力: 韵律/情感)
```

**这三个目标天然矛盾**:
- 要"好" (表现力丰富) → 需要更多信息 → 序列更长 → 更慢, 且 AR 建模更容易出错 → 不稳
- 要"稳" (不跳字/不幻觉) → 压缩信息/简化建模 → 丢掉韵律细节 → 不好
- 要"快" (低延迟) → 序列更短/模型更小 → 信息更少 → 不好, 且可能不稳

**行业所有 Token/Codec 设计的演进, 本质上都是在这个三角内寻找不同的权衡点。**

### 1.2 演进历程: 三次转向 (含论文原文依据)

```
时间线:   2023 ───────── 2024 ─────────── 2025 ──────────── 2026 ──→
          
第一阶段:  声学 token (RVQ 全量)
           ├─ SoundStream, EnCodec, DAC
           ├─ VALL-E, SoundStorm
           └─ 全部信息编进去 → "好"但不"稳"也不"快"

第二阶段:  语义 token (SSL/ASR 监督) + 声学分离
           ├─ CosyVoice (监督语义 token + Flow Matching)
           ├─ GLM-4-Voice (ASR-VQ, 175bps), Seed-TTS
           ├─ MaskGCT (SSL VQ-VAE 语义 token + 非 AR 掩码 + RVQ 声学补全)
           └─ 拆分信息到不同阶段 → "稳"了, 但"好"受限

第三阶段:  重新拥抱全量信息, 但换了建模方式
           ├─ DiSTAR (RVQ 全层 + masked diffusion, patch 级并行)
           ├─ DiTAR (连续向量预测, 不量化)
           ├─ WavTTS (直接波形 DiT, 彻底不要 codec)
           └─ 不做语义/声学拆分, 在全信息空间用新范式生成
```

#### 每次转向的论文原文依据

**第一阶段的问题 — 论文怎么说的:**

[[SoundStream]] 和 [[DAC]] 的设计目标是**通用音频压缩**, 不考虑 TTS 建模需求。SoundStream 论文原文关注的是"传统 codec (Opus, EVS) 在低码率 (<6kbps) 时严重退化" [SoundStream §I], DAC 关注的是"如何在 8kbps 实现 ~90x 压缩" [DAC §1]。两者都不讨论下游 LM 建模的 token 友好性。

当这些 codec 被用于 TTS 时, 问题暴露了:
- [[CosyVoice]] 明确指出: "无监督语音 token (HuBERT, EnCodec) 缺乏显式语义信息, 与文本的对齐质量差", 并给出了数据: **EnCodec token 做 TTS 的 WER 18.70%, HuBERT token WER 7.41%, 而监督 token WER 仅 3.93%** [CosyVoice §1, Table 7]
- [[MaskGCT]] 指出: "AR 系统 (VALL-E, VoiceCraft) 逐 token 生成导致鲁棒性差 (幻觉、重复)、推理速度慢" [MaskGCT §1]

**第二阶段的解决与代价 — 论文怎么说的:**

语义 token 路线解决了稳定性, 但引入了信息瓶颈:
- [[NaturalSpeech3]] 明确诊断了根因: "语音信号内在地纠缠了多种属性 (内容、韵律、音色、声学细节), RVQ 多层仍混合所有属性信息, 无法独立控制" [NaturalSpeech3 §1]。它提出 FACodec 做属性分解, 去掉分解后 SIM 下降 0.12, WER 上升 0.68 [NaturalSpeech3 Table 3]
- [[SAC]] 进一步指出: "纯声学 codec (EnCodec, DAC) 重建好但语义对齐差; 语义注入型 codec (X-Codec, SpeechTokenizer) 将语义和声学融合在一起, 两个优化目标互相干扰" [SAC §1]。SAC 的实验证明了干扰的严重程度: SemantiCodec 的语义流重建 WER 高达 30.67, 而 SAC 的冻结语义流仅 3.99 [SAC Table 5]
- [[MagiCodec]] 从另一个角度指出了问题: "neural audio codec 的重建质量和下游可建模性存在优化冲突...优化重建不能保证下游性能" [MagiCodec §1]

**第三阶段为什么"回去"了 — 论文怎么说的:**

- [[DiTAR]] 明确批评了两阶段级联: "离散 token AR + diffusion 精修 (VALL-E, CosyVoice): 两阶段级联导致误差累积, 限制了 LM 的 scaling 潜力" [DiTAR §1]
- [[DiSTAR]] 则批评了 DiTAR 的连续路线: "连续 latent diffusion (DiTAR/E2TTS 路线): 对分布偏移敏感, 高维优化脆弱, 通常需要 duration predictor" [DiSTAR §1]。DiSTAR 选择回到离散 RVQ 空间, 但用 masked diffusion 替代 AR
- [[WavTTS]] 最激进, 批评了所有中间表征: "Mel spectrogram 路线丢弃相位和高频信息, 需要额外 vocoder; VAE latent 路线高压缩导致信息损失, 多阶段训练引入累积误差" [WavTTS §1]

### 1.3 每次转向背后的逻辑

| 转向 | 面临的问题 | 解决思路 | 牺牲了什么 | 原文依据 |
|------|-----------|----------|-----------|---------|
| RVQ 全量 → 语义 token 分流 | AR 建模 RVQ 多层太难, 幻觉严重 | 只让 AR 建模"容易"的语义层 | 表现力天花板 | CosyVoice: 监督 token WER 3.93% vs EnCodec 18.70% |
| 语义 token → 重新拥抱全量 | 语义 token 丢了太多声学细节 | 新范式建模全量信息 | 方案复杂度 | DiTAR: "两阶段级联导致误差累积, 限制 scaling" |

**核心洞察**: 

> 不是"codec 选什么"在变, 而是**"谁来承担建模难度"**在变。第一阶段让 AR 扛全部, 扛不住; 第二阶段让 codec 做预处理减轻 AR 负担, 但压缩太多; 第三阶段让新的生成范式 (diffusion/mask) 替代 AR 来扛全量信息。

### 1.4 Codec 设计: 从"不考虑 TTS"到"专为 TTS 设计"

**早期 codec (2022-2023)**: 设计目标是通用音频压缩。[[SoundStream]] 论文关注"端到端低码率压缩" [§I], [[DAC]] 关注"8kbps 通用高保真" [§1]。[[Survey-DiscreteAudioTokens]] 系统梳理了这一阶段离散 token 的设计空间。

**现在的 codec (2025-2026)**: 设计时就在考虑下游 TTS 建模的需求:

| Codec | 权衡选择 | 为 TTS 解决了什么 | 论文原文依据 |
|-------|---------|-----------------|------------|
| **CosyVoice FSQ** | 稳 > 好 > 快 | 单码本+监督, LM 容易学 | CosyVoice2: FSQ 利用率 100% vs VQ 23%, ASR error 从 18.26% 降到 10.67% [Table 4] |
| **GLM 175bps** | 快 ≈ 稳 > 好 | 12.5Hz 极低帧率, 序列超短 | GLM-4-Voice: "SpeechLM 智能瓶颈在于语音数据稀缺", 用极低码率+合成数据解决 [§1] |
| **MagiCodec** | 稳 ≈ 好 > 快 | Gaussian 注入使 token 分布接近自然语言 | MagiCodec: mask 0%→30% TTS WER 从 5.51 降到 3.30; Zipf 分布分析显示 token 最接近自然语言 [Table 7, Fig 3] |
| **SAC** | 好 > 稳 > 快 | 双流分离, 语义流 SIM 仅 0.17 (几乎零说话人泄漏) | SAC: 语义流 WER 3.99 vs SemantiCodec 30.67 [Table 5] |
| **VARSTok** | 快 ≈ 好 | 变长 token, 自适应信息密度 | VARSTok: "固定帧率均匀分配 token, 忽视语音时变信息密度" [§1]; 36.81Hz UTMOS 4.00 vs WavTokenizer 40Hz 3.61 [Table 1] |
| **WavTokenizer** | 好 > 稳 | 单码本极致重建, 40 token/s | WavTokenizer: "多量化器 codec 给下游 LM 造成过度复杂性" [§1]; codebook 扩到 4096 实现 100% 利用率 [Fig 2b] |
| **无 codec** (WavTTS) | 好 >> 快/稳 | 零信息损失 | WavTTS: "所有中间表征都有信息损失"; 发现信号-噪声方差失配问题 (std 0.12 vs 1.0), 不修正 SIM 仅 0.32 [§3.3.1, Table 4] |

## 二、业界重点同行的技术演进

> 本节追踪 5 个重点同行团队的论文脉络, 从他们的技术路线演变推断其战略判断。

### 2.1 字节 (Seed-TTS → DiTAR → DiSTAR → WavTTS)

**论文序列**: [[Seed-TTS]] (2024.06) → [[DiTAR]] (2025.02, ICML) → [[MagiCodec]] (2025.06) → [[DiSTAR]] (2025.10) → [[SpeechJudge]] (2025.11) → [[WavTTS]] (2026.06)

**演进轨迹**:

```
Seed-TTS          DiTAR              DiSTAR              WavTTS
(2024.06)         (2025.02)          (2025.10)           (2026.06)
离散token+         连续latent+         回到离散RVQ+         直接波形+
两阶段级联         patch AR+DiT       patch AR+mask diff    flow matching DiT
                   │                  │                    │
                   ↓                  ↓                    ↓
     问题:幻觉+    问题:连续latent     问题:所有中间表征
     误差累积       对偏移敏感          都有信息损失
```

**关键转折点及其原文动机**:
1. **Seed-TTS → DiTAR**: Seed-TTS 自己就发现了 RL reward hacking — "过度优化 WER 会牺牲自然度" [Seed-TTS §4.2]。DiTAR 不满足于两阶段级联, 明确说"两阶段级联导致误差累积, 限制 LM scaling 潜力" [DiTAR §1], 转向 patch 级连续向量预测
2. **DiTAR → DiSTAR**: DiSTAR 批评了自家前作的连续路线, 说"连续 latent 对分布偏移敏感, 高维优化脆弱" [DiSTAR §1], 回到离散 RVQ。结果: 0.3B 模型 WER 1.66% 超越 Human 1.80% [DiSTAR Table 1], 同时 CMOS +0.22 超过人类录音 [Table 2]
3. **并行探索 WavTTS**: 不走修补路线, 彻底跳过所有 codec, 但发现了信号-噪声方差失配这个根本问题 [WavTTS §3.3.1]

**战略判断**: 字节在**同时押注多条路线** — 离散 (DiSTAR) + 波形 (WavTTS) + 评估 (SpeechJudge) + codec 基建 (MagiCodec)。他们没有固定在一条路线上, 而是快速迭代, 每个新工作都明确指出前一个的不足。这表明他们判断: **token/codec 路线尚未收敛, 值得多路并行探索**。

**对我们的启示**: 字节的 SpeechJudge 发现一个重要事实: "所有现有客观指标在自然度判断上接近随机 — WER 57.9%, SIM 44.5%, UTMOS 53.7%" [SpeechJudge Table 2]。这意味着我们不能仅靠自动指标评估"好"。

### 2.2 MiniMax

**论文**: 无公开论文 (完全闭源)。但在多篇他人论文中被引用为 baseline。

**间接数据** (来自他人论文):
- [[GLM-TTS]] Table 3: MiniMax-Speech CER 0.83% (zh), WER 1.65% (en) — 两项均为所有系统最优
- [[Step-Audio2.5]] arena 评估中被列为主要竞品

**战略判断**: MiniMax 以零论文、纯产品路线做到了 TTS Arena #1 和多个 benchmark 最优。这说明: **工程优化和数据积累的价值可能被学术界低估**。他们在所有公开对比中的指标都排名顶尖, 但完全没有公开技术路线, 无法判断其 codec/token 选择。

**对我们的启示**: MiniMax 的存在提醒我们, 纯指标领先不等于技术路线清晰。我们需要既有指标优势, 也有可解释的技术路线。

### 2.3 阶跃/StepAudio

**论文序列**: [[Step-Audio]] (2025.02) → [[Step-Audio-EditX]] (2025.11) → [[Step-Audio2.5]] (2026.05)

**演进轨迹**:

```
Step-Audio v1          Step-Audio-EditX        Step-Audio 2.5
(2025.02)              (2025.11)               (2026.05)
130B SpeechLM +        3B 语音编辑              统一MoE基座 +
独立3B TTS decoder     合成对比数据+PPO         三分支特化(ASR/TTS/RT)
  │                      │                       │
  ↓                      ↓                       ↓
  AQTA+TTS 分离架构       语音编辑是低成本         "任务差异=操作模式差异
  (理解与生成分开)        属性控制方案             而非架构差异"
```

**关键转折点**:
1. **v1 → v2.5 的架构范式转变**: v1 用 AQTA+TTS 分离架构 (130B 理解 + 3B 生成), v2.5 完全统一为一个 MoE backbone。v2.5 原文明确说: "一旦文本和音频共享良好的多模态表征空间, 下游任务差异不再是架构差异, 而是操作模式差异 — 数据构造、优化目标和解码约束" [Step-Audio2.5 §1]
2. **v2.5 TTS 完全取消 encoder-adapter**: 音频 token 被视为 LLM 词表中的"新语言", TTS 变成纯 next-token prediction [Step-Audio2.5 §2.2]
3. **EditX 的独立探索**: 不追求完美的表征解耦 (which is hard), 而是用**大间距合成对比数据**教 LM 编辑属性 [Step-Audio-EditX §3]。3B 模型迭代编辑: 情感准确率从 53.5% 到 70.7% (3 轮) [Table 1]

**战略判断**: 阶跃在走**统一大模型 + RLHF 全覆盖**路线。v2.5 用 Generative Reward Model (GRM) 做 TTS RLHF, Arena 整体胜率 69.1% [Fig 4]。EditX 则提供了一个**不需要重新设计 codec 就能提升可控性**的路径。

**对我们的启示**: 
- EditX 证明了**属性编辑是低成本提升可控性的路径** — 3B 模型就能改善 MiniMax、Doubao、GPT-4o-mini-TTS 的情感表达, 无需改动底层系统
- v2.5 的 Generative Reward Model (用生成式模型做 reward 而非标量打分) 是 SpeechJudge 之后的又一个 RM 创新

### 2.4 小米/MiSpeech

**论文序列**: [[ZipVoice]] (2025) → [[ZipVoice-Dialog]] (2025) → [[OmniVoice]] (2026) + [[TTS-PRISM]] (2026, 与清华合作) + MiMo-Audio 基座

**小米的布局远比单篇论文广泛**, 形成了**生成 + 评估 + 基座**三条线并进的格局:

**演进轨迹**:

```
ZipVoice            ZipVoice-Dialog       OmniVoice
(2025)              (2025)                (2026)
NAR FM TTS          NAR 对话 TTS           600+ 语言 NAR TTS
Zipformer 123M      curriculum learning    discrete diffusion
RTF 0.0125 GPU      超越 Dia/MoonCast      WER 0.84% (zh)
  │                    │                     │
  ↓                    ↓                     ↓
  证明 NAR+FM           从单句到对话            从英语到全球语言
  可比 AR 质量          超越 10x 更大模型        CMOS +0.44 vs GT

                    MiMo-Audio (7B)         TTS-PRISM (12维)
                    音频理解基座              TTS 评估诊断
                    被 10+ 篇论文引用          去掉负样本 LCC
                    作为 baseline             暴跌至 0.150
```

**关键技术选择**:
1. **一致押注 NAR (非自回归)**: ZipVoice 用 flow matching, OmniVoice 用 discrete diffusion (masked generation), 但始终避免 AR — 与字节 (AR+patch) 和阿里 (AR+FM) 路线截然不同
2. **极致效率**: ZipVoice 仅 123M 参数, RTF 0.0125 GPU (比 F5-TTS 快 ~24-33x) [ZipVoice Table II]; ZipVoice-Dialog 123M 全面超越 1.6B Dia 和 2.7B MoonCast [ZipVoice-Dialog Table 5]
3. **OmniVoice 的突破性指标**: 600+ 语言覆盖, Seed-TTS zh WER 0.84% / SIM 0.777 [OmniVoice Table 1], CMOS +0.44 vs ground truth [Table 8] — 在多语言和中文上均达到了顶尖水平
4. **评估基建**: TTS-PRISM 的 12 维诊断框架发现: 去掉对抗负样本后 LCC 从 0.717 暴跌至 0.150 — 比不训练的 baseline (0.320) 还差 [TTS-PRISM §4.1]; MiMo-Audio 7B 在 8/12 维度上超过 Gemini-2.5-Pro (30B+)

**战略判断**: 小米在走**NAR 路线 + 效率优先 + 评估基建**三条线。ZipVoice 将 ASR 领域的 Zipformer 架构迁移到 TTS, 实现了极致效率。OmniVoice 的 600+ 语言 + SOTA 中文指标表明, **NAR 路线在质量上已经不输 AR**, 而效率优势明显。MiMo-Audio 作为多篇论文的 baseline, 正在成为音频理解领域的通用基座。

**对我们的启示**: 
- OmniVoice 证明 NAR (masked generation + LLM init) 可以做到 WER 0.84% (zh), 与最好的 AR 系统 (CosyVoice3 0.71%) 差距很小, 但推理效率更高
- TTS-PRISM 的 12 维评估框架可直接作为方向三的参考, 特别是它区分了"能否表达情感" (Expression) 和"情感是否一致" (Consistency)
- ZipVoice 的**小模型高效率**路线 (123M 超越 1B+ 模型) 提醒我们效率也是竞争力

### 2.5 小红书/FireRedTTS

**论文序列**: [[FireRedTTS]] (2024.09) → [[FireRedTTS2]] (2025.09)

小红书是国内 TTS 领域投入最系统的互联网公司之一, 两篇论文之间实现了从**单句独白到多人对话**的完整跃迁。同时, FireRedTTS 作为 baseline 出现在大量他人论文中 (IndexTTS, GOAT-TTS, MSR-Codec, RWKVTTS, Semantic-VAE, UDDETTS 等), 表明其在行业中已成为公认的竞争性参照系。

**演进轨迹**:

```
FireRedTTS v1                          FireRedTTS-2
(2024.09)                              (2025.09)
─────────────────────                  ─────────────────────
数据: 624K→248K h (40%保留率)            数据: 1.1M h 独白 + 300K h 对话
Tokenizer: HuBERT (自监督) + ECAPA-TDNN  Tokenizer: Whisper (监督) + RVQ 16层
帧率: 标准                               帧率: 12.5Hz (4x下采样)
架构: 400M AR Transformer                架构: Dual-Transformer (Qwen2.5)
       + 双路线解码 (FM离线/Streaming在线)        (大backbone + 小decoder)
控制: 13种显式情感标签+副语言token         控制: 上下文隐式推断情感
场景: 单句独白 TTS                         场景: 多人对话+播客 (3分钟/4说话人)
  │                                        │
  ↓                                        ↓
  CER 2.09% vs CosyVoice 5.68%            CER 1.14% (zh), WER 1.95% (en)
  CoMOS 4.32 vs CosyVoice 4.15            Podcast CER 2.08 beat MoonCast 3.81
  情感准确 97-100% (fine-tuned)             情感准确 83-93% (6 emotions, 隐式)
```

**关键技术选择及论文依据**:

1. **数据管线是隐含的核心壁垒**: v1 详细描述了五步工业级数据管线 — 源分离→语音增强→VAD分割→说话人聚类→ASR转写→三维过滤 (DNSMOS>3.3 + 滚降频率>7kHz + ASR置信度>0.8), 从 624K 小时原始音频清洗到 248K 小时 (保留率仅 40%) [FireRedTTS §2, Fig 2]。v2 进一步将训练规模扩展到 1.1M 小时独白 + 300K 小时多说话人对话 [FireRedTTS-2 §2.2]

2. **Tokenizer 从自监督到监督的转变**: v1 用 HuBERT (自监督) + ECAPA-TDNN + Clip&Shuffle 防泄漏, v2 完全重新设计, 换成 Whisper encoder (监督) + 独立声学 encoder + RVQ (16层, 2048 entries) [FireRedTTS-2 §2.1]。这一转变与 CosyVoice 一直用监督 token 的路线趋同, **暗示自监督 tokenizer 在工业场景中表现不及监督方案** [agent 解读, 见 FireRedTTS 笔记]

3. **12.5Hz 超低帧率是对话场景的关键设计决策**: v2 将 Whisper 50Hz 特征 4x 下采样到 12.5Hz, 使 3 分钟对话的 token 数从 9000 缩减到 2250 [FireRedTTS-2 §2.1]。代价是每帧编码 80ms 信息 (标准 40ms 的两倍), 需要更大 codebook (2048 vs 1024) 和更多 RVQ 层 (16层)。但对于长对话场景, 这一 trade-off 非常值得 — 它使 transformer 的二次注意力复杂度显著降低

4. **Dual-Transformer 架构**: v2 用 backbone transformer (Qwen2.5, 大) 预测第 1 层 RVQ + decoder transformer (Qwen2.5, 小) 生成剩余 15 层, 论文明确说比 MusicGen 式 delay pattern 更优: "(1) 每个时间步完整访问之前所有 speech tokens; (2) 首帧全 N 层 token 仅需 1 步 backbone + N-1 步 decoder" [FireRedTTS-2 §2.2]

5. **从显式到隐式情感控制**: v1 用 emotion embedding + paralinguistic behavior token 显式控制 13 种副语言行为 (情感 fine-tuned 准确率 97-100%) [FireRedTTS Table 7]; v2 通过 text-speech interleaved format 保留完整前文 context, 使模型从上下文隐式推断情感 (6 类情感准确率 83-93%) [FireRedTTS-2 §3.2, Table 3]。**足够的上下文建模可以替代显式控制** — 这是方向二 (in-context 韵律) 的关键实证

6. **三阶段课程学习**: 独白预训练 (1.1M h) → 对话后训练 (300K h, 2-5 speakers) → SFT [FireRedTTS-2 §2.2], 渐进式从简单到复杂

7. **双模式部署**: v1 就提出了 flow-matching (高质量离线配音) + streamable decoder (低延迟在线聊天) 共享同一 LM 和 tokenizer 的方案 [FireRedTTS §3.3], v2 进一步将 first-packet latency 压缩到 <100ms [FireRedTTS-2 §5]

**竞争力量化**:

| 指标 | FireRedTTS v1 | FireRedTTS-2 | 对比 |
|------|:---:|:---:|---|
| CER (zh) | 2.09% | 1.14% | v1 已胜 CosyVoice 5.68%; v2 接近 Seed-TTS 1.12% |
| WER (en) | 12.00% | 1.95% | v1 英语较弱; v2 大幅提升, 接近 Seed-TTS 1.83% |
| SIM (zh) | — | 0.736 | 低于 Seed-TTS 0.796 但高于 MaskGCT 0.774 → 中上水平 |
| 情感准确率 | 97-100% (4类, 显式) | 83-93% (6类, 隐式) | 隐式准确率略低但覆盖更多情感且更自然 |
| 对话能力 | 无 | 3分钟/4说话人 | Podcast CER 2.08 beat MoonCast 3.81, MOSS-TTSD 3.99 |
| 数据规模 | 248K h (清洗后) | 1.4M h (独白+对话) | 数据规模从 25 万小时跃升到 140 万小时 |

**战略判断**: 小红书在走**从单句到对话的完整路径**, 是国内唯一系统性布局对话 TTS 的互联网公司。两个版本之间的技术选择演变 — tokenizer 从自监督到监督、情感从显式到隐式、场景从独白到对话 — 每一步都有清晰的工程动机。3 分钟/4 说话人是当前公开系统中最强的对话 TTS 能力之一。更重要的是, v1 的数据管线设计 (五步清洗, 40% 保留率) 和 v2 的三阶段课程训练, 展示了**系统工程能力而非单点学术创新**的竞争壁垒。

**对我们的启示**: 
- **12.5Hz 帧率是对话场景的关键技术选择** — 低帧率 = 长上下文 window 内放更多对话历史, 这是方向二的基础设施
- **Dual-transformer 优于 delay pattern** — 每个时间步完整看到所有历史 token, 首帧延迟更低 [FireRedTTS-2 §2.2]
- **情感从显式控制到上下文推断** 是方向二 (in-context 韵律) 最直接的实证参考: 97-100% 显式 → 83-93% 隐式, 用户感知反而更自然
- **数据管线的系统化** (源分离→增强→聚类→ASR→三维过滤) 是工业级 TTS 的基础, 而非只追求模型创新
- **监督 tokenizer 趋势被再次确认**: v1→v2 的 HuBERT→Whisper 转变, 加上 CosyVoice 一直用监督 token, 说明自监督 tokenizer 在工业 TTS 中可能已被淘汰

### 3.3 Post-training: 行业标配的实证基础

从 2024 年字节首创 TTS RL, 到 2026 年已成行业标配 (5+ 家采用), 但**每家都发现了不同的问题**:

| 团队 | 方法 | 发现的问题 | 论文依据 |
|------|------|-----------|---------|
| **字节** | REINFORCE → DPO → SpeechJudge | RL reward hacking: 过度优化 WER 牺牲自然度 | Seed-TTS §4.2 |
| **阿里通义** | DiffRO (token 级可微分 reward) | FM+vocoder 有去噪能力, 会"纠正" LM 级质量变化, 导致 MOS 控制瓶颈 | DiffRO §4.3.2, Table 4 |
| **RRPO** (在 DiffRO 基础上) | 三层混合正则化 | DiffRO 的全可微优化放大了 RM 缺陷: E-MOS 提升但 N-MOS 下降到 SFT 以下 | RRPO Table 1: DiffRO N-MOS 3.61 < SFT 3.72 |
| **GRPO-TTS** | CER+NLL 复合 reward | CER 大幅下降 (Llasa -83%) 但 MOS 不变 | GRPO-TTS §3.2.3 |
| **智谱** | GRPO 四维 | Dynamic Sampling 解决梯度消失 | GLM-TTS §5 |
| **SpeechJudge** | 专用 naturalness RM | 所有自动指标在自然度判断上接近随机 | SpeechJudge Table 2: UTMOS 53.7% |

**关键观察**: **RL 对 TTS 的"稳" (CER/WER) 效果显著, 但对"好" (自然度/表现力) 效果有限甚至有害**。GRPO-TTS 让 Llasa CER 下降 83% 但 MOS 不变; RRPO 发现 DiffRO 让自然度反而下降。这说明我们的方向三 (属性对齐 RL) 面临的核心挑战不是"RL 能不能用", 而是"reward 怎么设计才不 hack"。

## 四、我们在哪里, 要去哪里

### 4.1 PilotTTS 的位置

[[PilotTTS]] 选择了"稳定性优先"的路线:

```
设计选择链:
  CosyVoice FSQ 单码本 (选了稳)
    → 语义 token, 信息有限 (牺牲了好)
      → Q-Former 隐式补 style (试图补回一些好)
        → 但隐式建模有天花板 (好的上限被 codec 决定了)
```

**结果**: 
- ✅ 稳定性 SOTA (SIM 0.862, CER 0.87%) — SEED-TTS-Eval 最高 speaker similarity
- ✅ 数据效率高 (200K h 超越百万级)  
- ✅ 多维控制 (情感 88.1%, 副语言 85.1%, 14 种方言)
- ❌ 表现力天花板受限 (Q-Former 隐式 + 单码本容量有限)
- ❌ 无上下文韵律能力

### 4.2 目标: 在三角里移动位置

```
当前位置:     稳 >> 好 > 快
       ↓
目标位置:     稳 ≈ 好 > 快      (维持稳的同时, 把"好"拉上来)
```

**关键约束**: 稳定性不能退步 (SIM > 0.85, CER < 1% 作为硬约束)。

## 五、三个规划方向 — 从"快、稳、好"三角出发

### 方向一: 提升"好"的天花板 — Token/架构重新设计

#### 核心认识 (有实证支撑)

**表现力天花板由 codec/token 决定, 不是由模型大小决定的。**

实证依据:
- [[CosyVoice3]] 从 0.5B 升到 1.5B, 发现"更大模型在困难样本上甚至欠拟合, 说明瓶颈不在模型大小, 而在高质量 post-training 数据" [CosyVoice3 §5.1]
- [[Seed-TTS]] 明确把 tokenizer 称为"整个系统的瓶颈" [Seed-TTS §2]
- [[NaturalSpeech3]] 用相同 VALL-E 框架, 仅替换 FACodec 就在所有指标上提升 (SIM +0.12, WER -0.68) [NaturalSpeech3 Table 6]

#### 可选路线及实证

| 方案 | 对"好" | 对"稳" | 实证 | 适合我们 |
|------|-------|-------|------|---------|
| **双流 (语义+声学)** | 高 | 低风险 | SAC: 语义流 SIM 0.17 (零说话人泄漏), TTS WER 0.90% (zh) [Table 5, 9] | ★★★★★ |
| **多码本 + 非 AR** | 很高 | 中 | DiSTAR: 0.3B 即 WER 1.66% < Human 1.80% [Table 1] | ★★★★ |
| **连续表征** | 最高 | 中 | DiTAR 自家后续 (DiSTAR) 批评了"对分布偏移敏感" [DiSTAR §1] | ★★★ |
| **单码本扩容** | 中 | 低 | WavTokenizer: K 从 1024 到 4096, 利用率 100% [Fig 2b] | ★★★ |
| **变长 token** | 高 | 中 | VARSTok: 36.81Hz UTMOS 4.00 vs WavTokenizer 40Hz 3.61 [Table 1] | ★★★★ |

**建议路线**: 短期保持 FSQ + 模型升 2B → 中期探索双流 codec → 长期探索变长 token

#### 架构配合

| 升级 | 目的 | 同行实证 |
|------|------|---------|
| 模型 → 2B | 充分利用新 token 信息容量 | CosyVoice3 1.5B 已验证可行; Llasa 证明 1B→3B→8B scaling law 成立 (ICML 2025) |
| LLM 权重初始化 | 加速收敛 | CosyVoice2: Qwen2.5 初始化使 CER 降 18.5% [Table 7] |
| 显式 Style Module | 替代 Q-Former 隐式 | Step-Audio-EditX 证明 3B 即可做属性编辑, 情感准确率 53.5%→70.7% [Table 1] |
| 多阶段训练 | 低质量 PT + 精选 CT + RL | CosyVoice3, FireRedTTS-2 (mono→dialogue→SFT) 均采用 |

### 方向二: In-context 韵律 — 从单句建模到上下文建模

#### 核心认识

上下文韵律是"好"之外的独立能力维度:
- 同一情感设定下多句话情感不退化 (Style Amnesia)
- 对话中的语调呼应
- 段落级"朗读感"

#### 同行已经在做什么

| 团队 | 做了什么 | 方案 | 实证 |
|------|---------|------|------|
| **小红书** (FireRedTTS-2) | 3 分钟多人对话 TTS | 12.5Hz tokenizer + text-speech interleaved + dual-transformer | CER 1.14%, 情感准确 83-93% [Table 2, 3] |
| **Sesame** (CSM) | 对话韵律 (Voice Presence) | RVQ multi-stream, 上下文感知 | 仅英语, 开源 (14.7K ★) |
| **学术** | 上下文韵律初步探索 | TextAwareContextAwareTTS: 文本上下文指导韵律; BorderlessLongSpeech: 跨句情感弧线; Audiobook-CC: 有声书上下文标注 | 均为初步, 非系统方案 |

**行业空白**: "对话韵律建模"和"长文本一致性 (> 10 分钟)" 在 30+ 团队调研中被列为最大技术空白。

#### 小红书的经验可以借鉴

FireRedTTS-2 有几个关键技术选择值得参考:
1. **12.5Hz 帧率**: 低帧率 = 上下文 window 内放更多历史, 3 分钟对话从 9000 token 缩到 2250 [§2.1]
2. **情感从显式到隐式推断**: v1 用 13 种显式标签, v2 从上下文自动推断 — 更自然 [§3.2]
3. **三阶段课程**: 单人独白 (1.1M h) → 对话 (300K h) → SFT — 渐进学习 [§3.1]
4. **Dual-transformer 优于 delay pattern**: 每个时间步完整看到所有历史 token [§2.2]

#### 需要的资源

| 资源 | 说明 | 优先级 |
|------|------|--------|
| **Context 数据** | 段落级有声书, 对话播客 | P0 |
| **高表现力标注工具** | sentence-to-sentence 韵律变化模式 | P0 |
| **多人重叠检测** | 对话 10-20% 是 overlap | P1 |
| **对话级评测** | 跨句一致性评估 (行业无标准) | P1 |

### 方向三: 语音属性评价 & 标注 & 强化 — 优化闭环

#### 核心认识 (有实证)

**"好"的评估是当前行业公认的痛点**:

字节 SpeechJudge 的核心发现: "所有现有客观指标在自然度判断上接近随机 — WER 准确率 57.9%, SIM 44.5%, UTMOS 53.7%" [SpeechJudge Table 2]。这意味着: **我们日常用来评估 TTS "好不好" 的指标, 其实什么都没告诉我们。**

**RL 优化"好"很难, 容易 hack**:

| 发现 | 出处 |
|------|------|
| 过度优化 WER 牺牲自然度 | Seed-TTS §4.2: RL reward hacking |
| DiffRO 的 N-MOS (3.61) 下降到 SFT (3.72) 以下 | RRPO Table 1: "策略找到了有害捷径 — 生成微妙声学伪影骗 RM" |
| CER 大幅下降 (-83%) 但 MOS 不变 | GRPO-TTS §3.2.3: Llasa-1B 结果 |
| FM+vocoder 的去噪能力"纠正" LM 级质量变化 | DiffRO §4.3.2: MOS 控制瓶颈 |

**没有人做 Instruct-Following 评估** — 这是我们的差异化机会:
- [[InstructTTSEval]] 是唯一的 instruct following 评测集, 但只有评测, 没有训练好的 RM
- [[NoVerifiableRewardforProsody]] 深入讨论了韵律优化中 reward 难以验证的理论问题

#### 同行的评估工具现状

| 工具 | 评价什么 | 做了什么 | 没做什么 |
|------|---------|---------|---------|
| [[SpeechJudge]] (字节) | 自然度偏好 | 99K 成对偏好数据 + GRM (77.2%) | 不做 instruct following |
| [[TTS-PRISM]] (小米) | 12 维诊断 | 发音/韵律/情感/节奏等细粒度 | 诊断但不优化 |
| [[DiffRO]] (阿里) | token 级 reward | 绕过 FM+vocoder 直接优化 | 发现了 MOS 控制瓶颈 |
| Step-Audio-EditX (阶跃) | 属性编辑 | 合成对比数据+PPO | 编辑而非生成阶段的 RL |

#### 分层标注 + Reward Model + RL 闭环

```
分层标注 → 训练 RM → RL/DPO 优化 → 更好的 TTS → 生成新样本 → 标注 → ...
```

**我们的差异化: 属性对齐 RL** (让 TTS 精确遵循控制指令), 而非行业普遍做的通用质量 RL。

具体 RM 类型:

| RM 类型 | 输入 | 输出 | 防 hack 措施 |
|---------|------|------|-------------|
| **Instruct-Following RM** | (指令, 音频) | 遵循度 | 参考 RRPO 三层正则化 [RRPO §3] |
| **属性级 RM** | (音频, 目标属性) | 匹配度 | 多维度 Pareto (GRPO-TTS 思路) |
| **诊断 RM** | 音频 | 12 维评分 | TTS-PRISM 框架 + 对抗负样本 |

## 六、三个方向的关系与优先级

```
方向一 (Token/架构)   → 扩大三角的边界 (提升"好"的天花板)
方向二 (In-context)   → 增加一个维度 (从三角变四面体)
方向三 (评价/强化)    → 在边界内精准移动位置 (用 RL 最大化当前天花板下的"好")
```

```
                    ┌─────────────────────────────────────────┐
                    │  方向三: 评价 & 标注 & 强化 (闭环工具)    │
                    │  "怎么衡量好不好, 怎么变得更好"            │
                    └──────────┬──────────────┬───────────────┘
                               │              │
                    Reward 信号 ↓              ↓ 数据标注
                    ┌──────────┴──┐    ┌──────┴───────────┐
                    │ 方向一:       │    │ 方向二:            │
                    │ Token/架构   │    │ In-context 韵律   │
                    │ (天花板提升)  │    │ (场景扩展)         │
                    └─────────────┘    └──────────────────┘
```

**优先级**:
1. **方向一是前提**: Token 不升级, "好"的天花板就在那里 (Seed-TTS: "tokenizer 是整个系统的瓶颈")
2. **方向三和方向一并行**: RL 工具链可以在旧 token 上先验证 (但要注意 RRPO 发现的 reward hacking 风险)
3. **方向二在方向一成熟后扩展**: 单句表现力够了再考虑跨句 (小红书的经验: 先 mono PT 再 dialogue)

## 七、总结

### 行业本质叙事 (有论文实证)

```
2023:  Codec 是"通用音频压缩" → TTS 被迫适配
       SoundStream/DAC 目标: 低码率高保真压缩, 不考虑 TTS

2024:  发现问题, 为 TTS 设计 codec → 语义 token 崛起
       CosyVoice: 监督 token WER 3.93% vs EnCodec 18.70%
       Seed-TTS: "tokenizer 是整个系统的瓶颈"

2025:  稳定性解决, 表现力成新瓶颈 → 重新拥抱全量信息
       DiTAR: "两阶段级联限制 scaling" → 连续表征
       DiSTAR: "连续 latent 对偏移敏感" → 回到离散但用 mask diff
       SAC: "语义注入型 codec 两个目标互相干扰" → 物理分离双流

2026:  分化 + 评估觉醒
       WavTTS: 彻底跳过 codec, 发现波形空间根本问题 (方差失配)
       SpeechJudge: "所有自动指标在自然度上接近随机"
       各家选不同的"快/稳/好"权衡点
```

### 我们的机会

**我们已经拿到了"稳"的先发优势。** 行业已经过了"稳"是核心瓶颈的阶段。

下一步竞争焦点是**可控的"好"**: 我让它怎么表达, 它就怎么表达, 而且我能度量它做得对不对。

```
  通用表现力 (字节/阿里在追求的)     可控表现力 (我们要做的)
  ─────────────────────────       ─────────────────────────
  "随机地好听"                      "精确地好听"
  "评估靠 MOS" (SpeechJudge 证明    "评估靠属性匹配度"
    自动指标接近随机)                 (TTS-PRISM 12维+instruct RM)
  "RL 目标: 通用偏好"               "RL 目标: instruct following"
  (GRPO-TTS: CER降83%但MOS不变)   (属性对齐, 防 reward hacking)
```

### 一句话

> **从 codec 演进看, 行业正在从"为稳定性压缩信息"转向"用新范式建模全量信息"。同行的演进轨迹表明: 字节在多路并行探索 (离散/波形/评估), 阶跃在走统一大模型+RLHF, 小红书在做对话场景, 小米在做评估基建, MiniMax 以零论文做到指标第一。我们的策略是: 在升级 token 提升表现力天花板的同时, 建立"属性评价→标注→强化"的闭环, 做到可控的表现力 — 不是随机地好, 而是精确地好。**
