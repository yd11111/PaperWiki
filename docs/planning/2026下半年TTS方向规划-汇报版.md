>
> 基于: 行业调研 (30+ 团队/实验室) + PilotTTS 技术复盘 + PaperWiki 知识库 (257 篇论文)

## 一、TTS 领域现状: 发生了什么

### 1.1 行业共识架构已经形成

2024-2026 年，TTS 领域收敛到了一个主流范式:

```
文本 → [LLM AR 解码器] → 语义 token → [Flow Matching / DiT] → 声学特征 → 波形
```

**采用者**: CosyVoice (阿里), Seed-TTS (字节), GLM-TTS (智谱), Spark-TTS (NPU), StepAudio (阶跃), Qwen3-TTS (阿里 Qwen), PilotTTS (我们) 等几乎所有主流系统。

这意味着: **架构本身已不是差异化来源**。各家的差异化来自三个层面:
1. **Tokenizer/Codec 设计** — 10+ 种路线并存，分歧最大
2. **Post-training (RL/DPO)** — 从 1 家 (字节, 2024) 到 5+ 家 (2026)，成为新标配
3. **数据工程 + 控制能力** — 决定了系统的实际可用性

### 1.2 行业面临的三个根本问题

| 问题 | 表现 | 现状 |
|------|------|------|
| **稳定性 vs 表现力** | AR 模型的幻觉/跳字 vs 丰富的韵律表达 | 行业普遍未解决; 大多数系统二选一 |
| **单句 vs 上下文** | 逐句合成 vs 段落/对话级韵律连贯 | 极少系统考虑上下文; 对话场景尤其突出 |
| **可控性的评价闭环** | 控制了什么、效果如何、如何改进 | 缺乏统一评价体系; RL 对齐缺 reward model |

这三个问题正好对应我们后面要规划的三个方向。

### 1.3 行业各方在做什么

#### 国内核心团队

| 团队 | 核心路线 | 规模 | 差异化押注 | 与我们的关系 |
|------|----------|------|------------|------------|
| **阿里通义** (CosyVoice 3) | LLM + FM, 监督语义 token | 1.5B, 1M h | 监督 token + DiffRO (可微分 reward) | 我们的 tokenizer 来源; 直接竞品 |
| **字节** (Seed-TTS) | DiT 系列 | 极大 (未公开) | DiT 架构 + 评估标准主导 | 技术路线不同 (DiT vs FM) |
| **阶跃** (StepAudio 2.5) | 130B 统一大模型 | 130B→7B | RLHF 三模式全覆盖 | 规模路线不同; RLHF 思路可借鉴 |
| **智谱** (GLM-TTS) | 超低码率 (175bps) | 9B→1.5B | 单 codebook 12.5Hz, 极低码率 | codec 设计思路可参考 |

| **NPU/Soul** (Spark-TTS) | LLM AR + SAC 双流 codec | 1B/3B/8B | 全栈开源 + Scaling Law | SAC codec 设计值得研究 |

| **Google/Gemini** | LLM-native TTS (语音作为原生输出模态) | 大厂内部 | TTS 可能被 LLM 吞并的趋势 |

#### 学术界趋势

- **微软 TTS 研究团队已解体** — NaturalSpeech/VALL-E 系列停更, Xu Tan 离开
- **NTU 李宏毅**: 全面转向 Spoken Language Model + 全双工评测
- **X-LANCE (SJTU)**: 离散 token + 全双工对话 + Flow Matching, 与字节深度合作 (DiSTAR, WavTTS)
- **CUHK-SZ 武执政**: MaskGCT (非 AR TTS 标杆, ICLR 2025, 210 引用)

### 1.4 技术路线的核心分歧

**分歧最大的是 Tokenizer 层** — 至少 10 种路线并存:

| 路线 | 代表 | 特征 | 状态 |
|------|------|------|------|
| 监督语义 token | CosyVoice (阿里) | ASR/TTS 多任务监督, 高语义保真 | 验证最充分 |
| 超低码率单 codebook | GLM (智谱, 175bps) | 12.5Hz, 序列极短 | 极致效率 |
| 语义-声学双流 | SAC (NPU/Soul) | 双流分离, 各自优化 | 学术新意高 |
| 连续表征 | DiTAR (字节), VoxCPM (面壁) | 无量化损失 | 有风险但有突破潜力 |
| 变长 token | VARSTok (阿里, AAAI 2026) | 自适应压缩率 | 刚提出, 蓝海 |
| 无 codec | WavTTS (X-LANCE/字节) | 跳过所有中间表征 | 刚出现 |

**这意味着**: tokenizer 还没有收敛, 路线选择直接决定系统天花板, 是最值得投入的基础层。

### 1.5 Post-training: 新标配

从 2024 年字节首创 TTS RL, 到 2026 年已成行业标配:

| 团队 | 方法 | 特色 |
|------|------|------|
| 字节 | RL → DPO → SpeechJudge (Reward Model) | 最完整迭代链 |
| 阿里通义 | DiffRO (可微分 Reward 优化) | 直接优化 reward, 不用 RL 近似 |
| 阶跃 | SFT→DPO→PPO/GRPO→RLHF (三模式) | 覆盖最全面 |
| 智谱 | GRPO (四维: CER+SIM+Emotion+Laughter) | 多维度同时优化 |
| Fish Audio | GRPO (语义准确性+指令遵循+声学偏好+音色) | 开源实践 |

**关键观察**: 所有团队的 RL 都聚焦于"通用质量提升", **没有团队做 Instruct-Following 的 RL 对齐** — 这是我们的差异化机会。

## 二、我们的技术储备: 站在哪里

### 2.1 PilotTTS 技术定位

PilotTTS 是我们发布的零样本 TTS 系统, 核心架构:

```
Text → Qwen3-0.6B AR → FSQ semantic tokens → DiT-CFM (300M) → mel → HiFi-GAN → waveform
                ↑                                    ↑
        CAMPPlus spk emb                    CosyVoice 3 tokenizer (FSQ, 25Hz, 6561)
        + Q-Former style tokens
```

### 2.2 当前优势

| 维度 | 数据 | 说明 |
|------|------|------|
| **稳定性 (SOTA)** | SIM 0.862 (test-zh), WER 1.50% (test-en) | SEED-TTS-Eval 最高 speaker similarity |
| **数据效率** | 200K h 超越百万级数据的 Seed-TTS | 证明 "数据质量 > 数据规模" |
| **Speaker 保真** | Q-Former 双路径 conditioning | 情感控制下 SIM 保持最好 |
| **多维控制** | 情感 88.1%, 副语言 85.1%, 14 种方言 | 同一框架内覆盖多种控制能力 |
| **数据管线** | 三阶段管线, 全部公开工具 | 可复现性高 |

### 2.3 当前短板 — 表现力天花板

| 短板 | 根因 | 影响 |
|------|------|------|
| **表现力上限受限** | Q-Former 隐式建模风格, 无显式 style module | 细粒度韵律表达不够丰富 |
| **单码本信息容量** | FSQ 6561 entries, 单码本 | 天花板低于多码本 RVQ, 扩展性受限 |
| **间接重建** | mel + vocoder, 非端到端 | 额外失真 |
| **上下文无感** | 逐句生成, 不考虑前后文 | 段落/对话场景韵律不连贯 |
| **评价体系缺失** | 无通用 Instruct-Following 评估 | 无法量化"控制得好不好", RL 无处着力 |

### 2.4 一句话总结

> **PilotTTS 做到了行业领先的稳定性, 但表现力上限受限于 tokenizer 容量和隐式风格建模。下一步的核心目标: 稳定性维持, 提升表现力天花板。**

## 三、规划方向

> 以下三个方向是互相支撑的: 方向一解决基础能力天花板, 方向二解决使用场景扩展, 方向三提供衡量和优化的闭环。

### 方向一: 稳定性与表现力的平衡 — 重新思考基础架构

#### 问题本质

TTS 领域存在一个根本性矛盾:

```
稳定性 (准确率, 不跳字, 不幻觉)  ←→  表现力 (丰富韵律, 情感变化, 自然停顿)
         ↑                                      ↑
    约束越强越稳定                          约束越松越有表现力
```

PilotTTS 目前偏向稳定性一端:
- FSQ 单码本 (6561) 信息容量有限 → 韵律细节被压缩
- Q-Former 隐式编码风格 → 无法精准操控
- 0.6B AR 模型 → 建模能力上限

**目标**: 在维持当前稳定性 (SIM > 0.85, CER < 1%) 的前提下, 显著提升表现力上限。

#### 思路 1: 重新设计 Token

当前 FSQ 单码本的局限是表现力天花板的最大瓶颈。可探索的方向:

| 方案 | 代表 | 优势 | 风险 | 与我们的适配性 |
|------|------|------|------|--------------|
| **语义-声学双流** | SAC (NPU/Soul) | 解耦语义和声学, 各自优化上限 | 两阶段训练复杂度 | ★★★★ 可在 CosyVoice 3 tokenizer 基础上扩展 |
| **多码本 RVQ** | DiSTAR (X-LANCE/字节) | 信息容量大幅提升 | 序列变长, 推理成本 | ★★★ 需配合 patch 并行等加速 |
| **超低码率优化** | GLM-4-Voice (175bps) | 序列极短, 效率高 | 信息丢失 | ★★★ 可作效率路线参考 |
| **连续表征** | DiTAR (字节), VoxCPM (面壁) | 无量化损失 | 训练难度高 | ★★ 风险大但潜力高 |

**建议路线**: 短期继续使用 CosyVoice 3 监督 token 验证其他模块 → 中期探索双流或变长 token 差异化。

#### 思路 2: 架构升级

| 维度 | 当前 | 升级方向 | 参考 |
|------|------|----------|------|
| **模型规模** | Qwen3-0.6B | 2B+ (甜点规模) | CosyVoice 3 (1.5B), Llasa (1-8B) |
| **训练策略** | 单阶段 | 多阶段 (低质量 PT + 精选 CT + RL PT) | CosyVoice 3, Qwen3-TTS |
| **权重初始化** | LLM 预训练 | 复用更大 LLM 权重 | Qwen3-TTS, GLM-4-Voice |
| **Style 建模** | Q-Former 隐式 | 显式 style module 或分层 conditioning | 独立探索 |

**关键**: 2B 是甜点规模 — CosyVoice 3 1.5B 已证明可行, 够大出效果, 够小迭代快。

#### 思路 3: 显式 Style 建模

Q-Former 的隐式建模是当前表现力天花板的直接原因。可考虑:

- 引入显式韵律预测器 (pitch/energy/duration) 作为 AR 的辅助信号
- 分层 conditioning: 全局 speaker identity + 段落级 style + word-level 韵律
- 参考 BatonVoice (NL instruct) 和 FlexiVoice 的控制架构

#### 行业对标

| 竞品 | 稳定性 | 表现力 | 策略 |
|------|--------|--------|------|
| CosyVoice 3 | 中高 | 中高 (DiffRO 提升) | 监督 token + 可微分 reward |
| Seed-TTS | 高 | 高 | DiT 大模型 + Attention Guidance 防幻觉 |
| StepAudio | 中 | 高 (RLHF) | 130B 统一大模型, 暴力出奇迹 |
| 我们 (PilotTTS) | **最高** | 中 | Q-Former + 数据工程 |
| **我们 (目标)** | **维持最高** | **高** | Token 升级 + 显式 style + RL |

### 方向二: In-context 韵律 — 从单句到上下文

#### 问题本质

当前几乎所有 TTS 系统都是"逐句生成":

```
当前: 句子1 → TTS → 音频1 | 句子2 → TTS → 音频2 | 句子3 → TTS → 音频3
                    ↑ 互相独立, 没有上下文关联
```

这导致:
- **段落级韵律断裂**: 连续段落听起来像拼接, 缺乏"朗读感"
- **对话场景不自然**: 一问一答之间韵律不协调
- **情感退化**: 多句合成后情感风格逐渐丢失 (李宏毅称为 "Style Amnesia")
- **多人重叠缺失**: 对话中的插话、反馈词 (嗯/是的) 无法建模

#### 思路 1: 数据层 — Context-aware 数据构建

**核心**: 要让模型学会上下文韵律, 首先需要有带上下文标注的数据。

| 数据类型 | 来源 | 标注内容 | 优先级 |
|----------|------|----------|--------|
| **段落级朗读** | 有声书, 播客独白段 | 句间停顿/语速变化/情感弧线 | P0 |
| **双人对话** | 播客, 电话录音 | turn-taking 时机, 反馈词, 语调呼应 | P0 |
| **多人对话** | 多人播客, 圆桌讨论 | 多说话人切换, 重叠/插话 | P1 |
| **情感连续** | 有声书角色对话段 | 跨句情感演变轨迹 | P1 |

**高表现力标注工具**: 需要建设的工具链:
- 段落级韵律标注 (不是 word-level, 而是 sentence-to-sentence 的韵律变化模式)
- 对话 turn 切分 + overlap 检测 (pyannote 基础上扩展)
- 情感轨迹标注 (跨多句的情感变化曲线, 非离散标签)

#### 思路 2: 模型层 — 上下文感知架构

| 方案 | 原理 | 参考 |
|------|------|------|
| **Extended context window** | AR 模型输入不只当前句, 包含前几句的 token/hidden state | CosyVoice 2 的流式方案可扩展 |
| **Segment-level planning** | 先规划段落韵律大纲, 再逐句填充 | 类似 LLM 的 CoT, 先想再说 |
| **隐式 context conditioning** | 从对话历史自动推断韵律, 无需显式标签 | Sesame CSM 的 Voice Presence 思路 |
| **对话级 speaker tracking** | 多说话人场景下保持各人特征不混淆 | 京东 JoyVoice, 小红书 PodAgent |

#### 思路 3: 多人重叠场景

对话中的多人重叠是一个特殊但重要的问题:

```
Speaker A: "所以这个方案——"
Speaker B:                    "对对，我觉得可以"  ← overlap
Speaker A:                                       "——可以这样做"
```

- **数据**: 真实对话中 overlap 占比 10-20%, 但现有 TTS 数据几乎全是干净单人
- **建模**: 需要多通道生成或 overlap-aware 序列建模
- **评估**: Full-Duplex-Bench (NTU) 提供了基础评测框架

#### 行业对标

| 团队 | Context 能力 | 方案 |
|------|-------------|------|
| **Sesame CSM** | 对话韵律 (Voice Presence) | RVQ multi-stream, 上下文感知语调 |
| **ElevenLabs** | 从对话内容自动推断情感 | 闭源; 不需要显式 instruct |
| **阿里** (Fun-Audio-Chat) | 全双工对话 | 双分辨率 (5Hz+25Hz) |
| **NTU** | 全双工评测 | Full-Duplex-Bench v1/v2 |
| **我们 (当前)** | **无** | 逐句生成 |
| **我们 (目标)** | **段落/对话级韵律连贯** | Context data + planning |

### 方向三: 语音属性评价 & 标注 & 强化 — 建立优化闭环

#### 问题本质

当前的困境:

```
控制了什么?     →  不确定 (缺乏细粒度属性定义)
控制得好不好?   →  不知道 (缺乏评价手段)
如何改进?       →  没有方向 (缺乏 reward 信号)
```

没有评价, 就没有优化方向; 没有标注, 就没有评价基础; 没有强化, 就无法闭环迭代。

**这是一个"评价→标注→强化"的三级火箭:**

```
分层级标注  →  评价模型 (Reward Model)  →  RL/DPO 强化  →  更好的模型  →  更精准的标注
   ↑                                                                        |
   └────────────────────── 数据飞轮 ──────────────────────────────────────────┘
```

#### 思路 1: 分层级标注体系

**当前行业标注现状**: 大多只标注 MOS (1-5 分主观评分) 或离散情感标签 (开心/悲伤/愤怒)。这远远不够。

**我们需要的分层标注**:

```
基础层: 文本对齐, 说话人 ID, 时间戳
    ↓
属性层: 情感 (连续值, 非离散标签), 语速, 音高轮廓, 能量包络
    ↓
细粒度层: word-level 情感, 副语言事件 (笑声/叹气/犹豫) 的位置和类型
    ↓
偏好层: 成对偏好 (A > B), 多维度打分 (自然度/表现力/一致性/instruct 遵循度)
```

**关键设计**: 
- 属性层使用**连续值**而非离散标签 — "情感不是'开心'或'悲伤', 而是一个连续空间"
- 偏好层需要**多维度**而非单一维度 — "A 的自然度好但情感表达差, B 反之" 的信息不能被压缩成一个数字

#### 思路 2: 评价模型 (Reward Model)

有了标注数据, 下一步是训练自动评价模型:

| 维度 | 评价什么 | 参考 |
|------|----------|------|
| **Instruct 遵循度** | TTS 输出是否遵循了指令 (说快一点→真的变快了吗?) | InstructTTSEval (刚出现) |
| **自然度** | 听起来自然吗? | UTMOS, SpeechJudge |
| **情感一致性** | 指定开心→是否真的开心? | emotion classifier |
| **音色保持** | 控制了情感后, 说话人音色变了吗? | SIM (speaker similarity) |
| **韵律丰富度** | 韵律多样且适当吗? 还是单调/过度? | ProsodyEval (字节) |

**核心创新点**: **Instruct-Following Reward Model for TTS** — 这是 NLP 领域 IF-Eval 到语音的直接迁移, 目前行业没有团队系统做过。

行业现有 RL 都是优化通用质量 (自然度+准确度+相似度), 没有人做 "TTS 是否遵循了控制指令" 的 RL — 这是我们可以差异化的点。

#### 思路 3: RL/DPO 强化

有了 Reward Model, 就可以做 RL 对齐:

| 阶段 | 方法 | 目标 |
|------|------|------|
| **快速验证** | LLM-as-Judge 做 proxy reward | 验证 RL for TTS instruct 的可行性 |
| **独立 RM** | 训练专用 Instruct-Following RM | 覆盖语速/音高/情感/停顿/强调等多维度 |
| **多维度平衡** | Pareto 优化 (自然度 + instruct 遵循度 + 音色保持) | 防止优化单一指标损害其他维度 |
| **防 Reward Hacking** | RRPO 思路 + 人工抽检 | 防止模型学会"取悦评估器"但不自然 |

#### 行业对标

| 团队 | RL 目标 | 与我们的区别 |
|------|---------|------------|
| **字节** (SpeechJudge) | 通用质量 (自然度+准确度) | 不做 instruct following |
| **阿里** (DiffRO) | 通用质量 (可微分 reward) | 优化方法新, 但目标相同 |
| **阶跃** (三模式 RLHF) | ASR准确/TTS偏好/实时体验 | 分场景但不做细粒度属性控制 |
| **我们 (目标)** | **Instruct Following + 多维度属性** | 差异化: 优化"控制是否准确" |

## 四、三个方向的关系

```
                    ┌─────────────────────────────────────────┐
                    │  方向三: 评价 & 标注 & 强化 (闭环工具)    │
                    │  "怎么衡量好不好, 怎么变得更好"            │

                               │              │
                    Reward 信号 ↓              ↓ 数据标注
                    ┌──────────┴──┐    ┌──────┴───────────┐
                    │ 方向一:       │    │ 方向二:            │
                    │ 稳定性与表现力 │    │ In-context 韵律   │
                    │ (基础能力)    │    │ (场景扩展)         │
                    └─────────────┘    └──────────────────┘
```

- **方向一**是基础: 表现力天花板不解决, 上下文韵律和属性控制都会受限
- **方向二**是场景扩展: 从单句到段落/对话, 覆盖更多实际使用场景
- **方向三**是闭环工具: 提供评价和优化手段, 持续改进前两个方向

三者的迭代顺序建议: 方向一 (基础能力) 和方向三 (评价工具) 先行, 方向二 (上下文) 在基础能力成熟后自然扩展。

## 五、与行业差异化定位

> **"稳定可控 + 属性对齐 + 高效流式"**

| vs | 他们的优势 | 我们可以差异化的地方 |
|----|----------|-------------------|
| **vs 通义** | 开源生态 + 数据规模 + 监督 token | Instruct 维度 (通义的 Instruct 能力弱, CosyVoice 主打 zero-shot) |
| **vs 字节** | DiT 架构 + 评估标准 + 极大模型 | 可控性 + 属性对齐 (字节更关注稳定性/音质, 不关注精细控制) |
| **vs 阶跃** | 130B 统一大模型 + 全覆盖 RLHF | 模块化 + 效率 (不需要 130B, 2B 精准控制更实用) |
| **vs Fish** | 开源影响力 + 多语言 | 闭环优化 (从标注→评价→强化的系统性方案) |

**不拼模型规模和数据量, 拼控制精度和对齐质量。**

| 风险 | 可能性 | 影响 | 缓解 |

## 附录: 行业趋势速览

### 上升趋势 (做的人越来越多)

| 方向 | 2024 | 2026 | 信号 |
|------|------|------|------|
| Post-training (RL/DPO/GRPO) | 1 家 | 5+ 家 | 行业标配 |
| 全双工/实时对话 | 2 家 | 7+ 家 | 首个竞赛 HumDial (ICASSP 2026) |
| Codec 设计创新 | 1-2 种 | 10+ 种 | 分化极快 |
| TTS 可控性 (自然语言指令) | 少量 | 多方 | Voice Design, EditX |
| Voice Agent | 1 家 | 5+ 家 | 占 YC 最新一期 22% |

### 三大范式转移

1. **独立 TTS → LLM-native 语音能力** — 语音成为 LLM 的原生输出模态
2. **手工特征工程 → Post-training 对齐** — 用 reward model 自动优化
3. **Transformer 独占 → 架构多元化** — SSM/DiT/Masked Generative 并行竞争

### 下降趋势

- 传统 Mel-spectrogram 声码器 — 被端到端替代
- 级联式 ASR+LLM+TTS — 被端到端多模态替代
- 小模型 TTS (< 100M) — 被 1B+ 大模型替代
- 微软 TTS 研究 — 核心团队解体
