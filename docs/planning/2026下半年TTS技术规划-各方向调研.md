## 一、Instruct 扩展 + 上下文 Conditioning

### 现状澄清：行业实际控制能力

"Instruct TTS"这个说法容易产生误解。需要先区分两件完全不同的事：

**结构化指令控制（绝大多数系统实际在做的）：**
预定义标签/标记集合，用户从中选择，不是自由输入。

| 系统 | 实际控制方式 | 本质 |
|------|------------|------|
| CosyVoice 2 | 情感/语速/方言/角色标签，1500h 指令数据 | 大标签集 |
| CosyVoice 3 | 100+ 种预定义风格 + `[laughter]`/`[breath]`/`<strong>` 标记，5000h 指令数据 | 大标签集 + 细粒度标记 |
| VoxInstruct | 统一指令格式但属性维度预定义（声学+说话人+情感+场景），SpeechCraft 标注系统 | 结构化属性组合 |
| CapSpeech | 9 属性 NL caption，维度固定 | 模板化描述 |
| BatonVoice | LLM 分解为 Hz/dB/ms 数值特征，TTS 接收数值不是文本 | 数值控制 |
| CoCoEmo/TED-TTS | 情感类别/方向向量注入，非文本输入 | 标签+激活操控 |
| AgentSteerTTS | 通过 prototype retrieval 映射到离散 style | 结构化组合 |

**真正的自然语言控制（少数系统做到的）：**
用户写任意自由文本描述风格/音色/情感，模型理解并执行。

**工业级系统（大规模预训练 + NL 控制）：**

| 系统 | NL 控制方式 | 数据规模 | 效果 | 局限 |
|------|-----------|----------|------|------|
| **Qwen3-TTS** (2025) | Voice Design: NL 描述创建声音 + 概率性 thinking pattern | 5M h 预训练 | APS-zh 85.2, DSD-en 82.4 (开源 SOTA) | voice design 细节披露少 |
| **Step-Audio 2.5** (2026) | Emotional-Context-Speech pipeline: MFA+声学特征 → LLM 生成 global+inline NL descriptions + GRM 对齐 | 2.2T tokens | TTS arena 69.1% win rate | 评估仅 arena，无标准 benchmark |
| **Fish Audio S2** (2025) | Qwen3-4B backbone + 自然语言 instruction following + GRPO RL 对齐 | 大规模 | 开源 | 指令仍偏标签式 ([whisper]/[angry]) |

**学术/开源系统（小规模数据 + NL 控制）：**

| 系统 | NL 控制方式 | 数据规模 | 效果 | 局限 |
|------|-----------|----------|------|------|
| **OV-InstructTTS** (2026) | 开放词汇叙事指令 + LLM reasoning chain | 476.8h 有声书 | MOS 4.28, Gemini 70.4 | 仅英文有声书 |
| **EmoVoice** (2025) | Freestyle NL emotion description + LLM 理解 | 40h NL + 200h 辅助 | Emo_Sim 0.91, Recall 0.42 | 仅情感维度 |
| **HD-PPT** (2026) | CLAP 对齐 NL prompt + 分层 preference tokens | TextrolSpeech + EmoVoice-DB | EMO-SIM 0.753 | RTF 0.95 |
| **VoiceSculptor** (2026) | CoT 属性推理 + RAG 补偿分布外指令 → 生成 prompt waveform → voice clone | — | — | 两阶段有信息瓶颈 |
| **MOSS-VoiceGenerator** (2026) | NL timbre/style 描述直接创建新音色（无参考音频） | 18K+7K h 影视数据 | DSD 82.0% | 影视数据偏 |
| **IndexTTS2** (2025) | T2E 模块: DeepSeek-R1 教师 → 蒸馏 Qwen3-1.7B 预测情感分布 → 加权混合 embedding | 135h 情感数据 | EMOS 4.22 (vs CosyVoice2 3.34) | 仅 7 类情感 |
| **DMP-TTS** (2025) | Style-CLAP: 文本描述/音频参考 → 统一 style embedding → DiT + cCFG | — | — | CLAP 覆盖范围受限 |
| **InstructTTS** (2023) | 自由 NL 风格描述 + RoBERTa 编码 | 44h 内部中文 | MOS 4.35 | 数据未公开 |

**NL 控制的数据基础设施（不是 TTS 系统，但是上游数据源）：**

| 系统 | 贡献 | 规模 |
|------|------|------|
| **SpeechCraft** (2024) | 自动标注 8 维属性 + LLaMA 定制化 NL 描述（非模板填充） | 2000+ h, EN+ZH |
| **CapSpeech** (2025) | 10M+ 机器标注 + 358K 人工标注的 audio-caption pairs | 大规模 |

**关键事实**：
1. 行业说的"instruct TTS"**存在明显分层**：CosyVoice 3 是大标签集控制（100+ 预定义风格），Qwen3-TTS / Step-Audio 2.5 才是真正的 NL 控制
2. **NL 控制效果与预训练规模强相关**：Qwen3-TTS (5M h, APS 85.2) >> EmoVoice (240h, Recall 42%)
3. **NL 控制的两种路线正在浮现**：
   - 端到端 NL 理解（Qwen3-TTS/EmoVoice）：LLM 直接理解自由文本 → 生成语音
   - 中间表征分解（OV-InstructTTS/IndexTTS2/BatonVoice）：LLM 将 NL 分解为结构化属性/数值 → TTS 执行
4. **数据构建正在从标签标注转向 NL 标注**：SpeechCraft (2000h NL 描述)、CapSpeech (10M 标注) 等数据集为 NL 控制提供基础
5. Fish Audio S2 的指令仍偏标签式 (`[whisper]`/`[angry]`)，离 freestyle NL 有距离

### 要解决的问题

基于上述现状，三件事的实际差距不同：

1. **控制标签扩展** — 当前路线已有，CosyVoice 3 做到 100+ 种。瓶颈不在方法而在**标注数据覆盖度**
2. **自然语言控制** — Qwen3-TTS 和 Step-Audio 2.5 已验证 NL 控制在**大规模预训练**条件下可行 (APS 85.2)。但在**中小规模数据**条件下 (EmoVoice 240h)，recall 仅 42%。关键问题是：我们的数据和算力条件下，走哪条 NL 路线能 work？
3. **上下文 conditioning** — 依赖 NL 控制或标签控制的基座，叠加上下文感知层

### 路线选择

```
Q1: 目标是什么级别的"可控"?

├── 扩展标签集 (工程导向, 可预期)
│   做法: 扩大标注维度和标签数量，在 CosyVoice 路线上 SFT
│   参考: 吧你不不不计划今年内吗。你  。。，你                       吗
│   瓶颈: 标注数据采集
│
├── 真正的 NL 控制 (工业级已有验证, 但数据/算力门槛高)
│   ├── 端到端 NL 理解 (LLM 直接理解自由文本 → 生成语音)
│   │   ├── 大规模: Qwen3-TTS 路线 (5M h, APS 85.2) / Step-Audio 2.5 路线 (2.2T tokens)
│   │   └── 小规模: EmoVoice 路线 (40h NL + LLM SFT, Recall 0.42) — 能力受限
│   ├── 中间表征分解 (LLM 将 NL 分解为结构化属性/数值 → TTS 执行)
│   │   ├── 推理链: OV-InstructTTS (reasoning chain, 仅英文有声书)
│   │   ├── 数值特征: IndexTTS2 (DeepSeek-R1→Qwen3→情感分布) / BatonVoice (Hz/dB)
│   │   └── CLAP 对齐: HD-PPT (preference tokens, EMO-SIM 0.753)
│   └── Voice Design (NL 描述 → 生成 prompt waveform → voice clone)
│       └── VoiceSculptor (CoT+RAG) / MOSS-VoiceGenerator (影视数据)
│
└── 上下文自动推断 (可与上述任一方案叠加)
    ├── 改动最小: plug-and-play encoder (TACA-TTS)
    ├── 效果最好但需重训: text-speech interleaved (FireRedTTS-2)
    └── 可解释但延迟大: LLM CoT 推理链 (Chain-Talker)
```

### 核心任务

**标签扩展方向（工程化路线）：**

| 任务 | 做什么 | 依赖 |
|------|--------|------|
| 标签维度设计 | 定义需要支持的控制维度和类别。参考 CosyVoice 3 的 100+ 种风格 | 无 |
| 标注数据采集 | 按维度标注语音数据（情感/语速/口吻/停顿/副语言等）| 标签维度 |
| Instruct SFT | 在现有架构上做 instruction-following SFT | 标注数据 |

**NL 控制方向（研究性路线）：**

| 任务 | 做什么 | 依赖 |
|------|--------|------|
| 搭建 NL-speech 标注 pipeline | 用 LLM 从语音自动生成 freestyle style description。参考 EmoVoice-DB (GPT-4o-audio)、CSS-EmCap (Gemini)、OV-InstructTTS ContextSpeech (Qwen3-32B) | 无 |
| 构建 NL 配对数据 | 起步 40-200h (EmoVoice 40h 即达 Emo_Sim 0.91)。数据量不是瓶颈——底座能力和数据质量更关键 | 标注 pipeline |
| NL Instruct SFT | 在 LLM-TTS 架构上做 freestyle NL instruction-following 微调 | NL 配对数据 |
| 评估体系 | 建立 NL instruct-following 评测。注意: 现有 Emotion Accuracy (SER) 仅评估情感维度，全维度评测需自建（参考 Gemini Score / InstructTTSEval） | 评价闭环 |

**上下文 Conditioning 方向：**

| 任务 | 做什么 | 依赖 |
|------|--------|------|
| 对话数据采集 | 获取多轮对话语音数据。来源: NCSSD (236h)、OpenDialog (6.8K h)、从 Emilia 筛选 | 无 |
| Context encoder 选型验证 | 在 2-3 种方案上做对比实验: plug-and-play encoder vs interleaved vs CoT | 标签扩展或 NL 控制的基座模型 |
| Instruct + Context 融合 | 设计优先级机制: 有显式指令走指令，无指令走上下文推断。当前无人做过 | Context encoder + 控制基座 |

**快速验证任务（可先做）：**
- 用 training-free 方法 (CoCoEmo activation steering / TED-TTS 2D mask) 在现有模型上测试情感控制范围 → 定义"当前模型的表达力边界在哪"
- 注意: 这些方法本身是标签级控制（输入情感类别而非自由文本），用于探测模型潜力而非实现 NL 控制

### 空白与机会

- **中文全维度 NL 控制的效果差距**: Qwen3-TTS 中文 APS 85.2 已不错，但其内部数据和算力门槛极高 (5M h)。在我们的资源条件下能做到什么水平，需要验证
- **中间表征分解路线在中文的验证**: OV-InstructTTS reasoning chain 仅英文，IndexTTS2 T2E 仅 7 类情感。中文全维度的分解路线是空白
- **对话+Instruct 融合**: 当前 CSS 系统和 Instruct 系统完全独立，融合无人做过
- **NL 控制两条路线的 trade-off 未被系统对比**: 端到端 NL 理解 vs 中间表征分解，哪条在有限资源下更优？没有论文做过 head-to-head
- **数据构建基础设施已就位**: SpeechCraft (2000h NL 描述) 和 CapSpeech (10M 标注) 等数据集可直接利用

### 风险与退路

| 风险 | 退路 |
|------|------|
| 端到端 NL 路线在我们的数据规模下 recall 不够 | 转中间表征分解路线 (IndexTTS2/BatonVoice)，或退到大标签集 |
| 全维度 NL 比仅情感难度大 | 先做情感维度（EmoVoice 路线），再逐步扩展维度 |
| 中间表征分解路线延迟大 | 选轻量分解 (IndexTTS2 蒸馏) 而非完整 reasoning chain |
| 上下文延迟太大 | 选 plug-and-play encoder 而非 CoT |
| 多属性组合 mode averaging | 先做单属性，后叠加 GRL 解耦 |

## 二、效率优化：低帧率 + 流式

### 要解决的问题

两个独立但可并行的维度：
1. **低帧率** — 减少 AR 序列长度（当前 50Hz → 目标 12.5Hz = 序列缩短 4x）
2. **文本流式** — 文本逐字到达即可开始合成（当前 FPL ~1000ms → 目标 <200ms）

### 路线选择

**低帧率：**

```
Q: 低帧率走什么路线?
├── 稳妥: 12.5Hz 监督降采样 (FireRedTTS-2 路线, Whisper+16层RVQ)
├── 激进: 6.25Hz + diffusion decoder (TaDiCodec, 风险高但序列最短)
├── 开源: 直接用 Mimi 12.5Hz (Kyutai 开源, finetuning)
└── 保守: 保持 25Hz + MTP 加速 (不换 tokenizer, 加 Llasa+ 风格 MTP 模块)
```

**文本流式：**

```
Q: 流式走什么方案?
├── Full-stream AR: text-speech interleaved (VoXtream2 路线, FPL 63-74ms)
├── 改造现有: chunk-based FM (CosyVoice 2 路线, 成熟但 FPL 高)
├── Voice Agent 集成: interleaved decoding (LLM hidden→speech decoder)
└── 端到端对话: inner monologue (Moshi 路线)
```

**两者可以独立并行或串行组合：**
- 路线 1: 先做 full-stream (在现有 tokenizer 上验证) → 再接 12.5Hz tokenizer
- 路线 2: 先做 12.5Hz tokenizer (重建验证) → 再在新 tokenizer 上做 full-stream
- 路线 3: 两者完全独立并行

### 核心任务

**低帧率方向：**

| 任务 | 做什么 | 关键判定 |
|------|--------|----------|
| 12.5Hz tokenizer 训练 | 训练或 finetune 12.5Hz streaming tokenizer (参考 FireRedTTS-2 / Mimi) | 重建 WER/SIM 在基线 95% 以内 → 继续；否则退到 25Hz |
| LM 适配 | 在 12.5Hz token 上重训 AR LM | 端到端 WER/SIM 不退 5% |
| 推理加速叠加 | MTP 模块 (Llasa+ 路线, +30-50%) + CUDA Graphs (+15%) | RTF < 0.3 |

**文本流式方向：**

| 任务 | 做什么 | 关键判定 |
|------|--------|----------|
| Forced alignment 数据构建 | 用 MFA/CTC 获取字粒度时间对齐 → 构建 text-speech interleaved 训练数据 | 覆盖主要数据集 |
| Full-stream AR 实现 | text-speech interleaved format + causal LM + multi-condition CFG (参考 VoXtream2) | FPL < 200ms + WER 不退 |
| 流式 vocoder | 将非因果 decoder 改造为因果流式 (参考 Llasa+ XCodec2-S) | 质量保留 95%+ |

### 关键指标约束

| 指标 | 硬约束 |
|------|--------|
| WER 退化 | 不超基线 +1% 绝对值 |
| SIM 退化 | 不低于基线 -0.03 |
| RTF | < 0.3 |
| FPL (如做流式) | < 200ms |

### 风险与退路

| 风险 | 退路 |
|------|------|
| 12.5Hz 重建质量不达标 | 退到 25Hz + MTP 加速 |
| Full-stream 韵律失控 | 加 lookahead buffer (50-100ms) 或 CFG 补偿 |
| 两者组合后退化叠加 | 分步验证，不一步到位 |

## 三、Tokenizer / 表示层路线验证

### 要解决的问题

当前 tokenizer (CosyVoice 路线, 25Hz FSQ ~300bps) 的**表现力天花板**：语义 token 丢失副语言信息，CFM 只能从 prompt 恢复已见风格。需要找到能在**不损 CER/SIM 前提下提升表现力**的路线。

### 路线选择

```
Q: 能接受多大架构改动?

最小改动 (仅换 tokenizer, LM 不变):
├── 大码本单码本 (MagiCodec-style): K=65K-131K, Gaussian noise, 单流 AR
│   已知: UTMOS 4.18, SPK-SIM 0.76, Zipf 分布 LM 友好
│   风险: 大词表 softmax 开销; 帧率仍 50Hz
│
└── 更低帧率监督 token (12.5Hz): 加 RVQ 层补偿
    已知: FireRedTTS-2 CER 1.14%, SIM 0.736
    风险: 16 层 RVQ 增加复杂度

中等改动 (LM head 修改):
├── 连续 latent (DiTAR-style): softmax → diffusion head
│   已知: WER 1.69, Q-MOS 3.87, scaling law 已验证
│   风险: SIM 退步 (0.735 vs 0.775) — 这是最大问题
│
└── 双流 (Qwen3-TTS-style): 加 acoustic refinement 分支
    已知: WER 0.77%, SIM 0.799, FPL 97ms
    风险: 长文本不稳定; 需 5M h 数据

大改动 (重写 pipeline):
├── 无 codec 波形 (WavTTS): 全 NAR, 直接 flow matching on waveform
│   已知: UTMOS 3.92 最高, 但 SIM 0.65 太低, 需 100K+ h
│
└── 属性分解 (NS3/FACodec): content/prosody/timbre/detail 四路
    已知: 理论最灵活, 但训练极复杂
```

### 核心任务

| 任务 | 做什么 | 产出 |
|------|--------|------|
| 基线锁定 | 在现有系统上跑全套评估 (SEED-TTS-Eval + 表现力测试集) | 基线报告 |
| 表现力度量定义 | 构建表现力测试集 (情感/语速变化/停顿/笑声/呼吸)；定义"表现力提升"的量化标准 | 评估 pipeline |
| Tokenizer 频域分析 | 用 Cont-SPT 方法做 transfer function 分析，量化当前 tokenizer 在哪些频段丢信息 | 瓶颈诊断 |
| 控制变量 PoC | 在 ~1000h 数据上，一次只变一个因素 (码本大小 / 帧率 / 离散vs连续 / 单流vs双流) | 路线选型依据 |
| 选定路线深度验证 | PoC 通过的路线扩到生产级数据 (万+h)，验证 scaling + RL 兼容性 + 流式 | 生产可行性 |

### 硬约束

| 约束 | 阈值 | 违反后果 |
|------|------|----------|
| SIM | >= 0.775 (当前基线) | 该路线否决 |
| CER/WER | <= 当前基线 | 该路线否决 |
| RTF | < 0.3 | 不能上线 |

### 风险与退路

| 路线 | 最大风险 | 退路 |
|------|----------|------|
| 大码本单码本 | LM 大词表不收敛 | 小规模先测；退到 FSQ |
| 连续 latent | SIM 退步 | 加 speaker conditioning；放弃走离散 |
| 双流 | 长文本不稳定 | 限制 acoustic 层长度；退回单流 |
| 极低帧率 | diffusion decoder 延迟 | consistency distillation；退到 12.5Hz |

## 四、评价与对齐闭环

### 要解决的问题

当前没有系统化评价体系，靠人工试听挑 demo。这是**基础设施**，支撑所有其他方向。需要建立的闭环：

```
评价体系 → Reward Model → Post-training → 新数据/迭代 → 评价体系
```

### 路线选择

**评价 vs 对齐的顺序：**

```
Q1: 先搞评价还是先搞对齐?
├── 评价先行: 先建自动评价 pipeline → 用于模型选型/AB-test → 再考虑 RL
└── 对齐先行: 直接跑 GRPO (零标注) → 看效果 → 再回头补评价
```

**Post-training 方法选择：**

```
Q2: 走什么 post-training 方法?
├── GRPO (零标注, 自动 reward): 当天可跑, 但 >1500 步可能退化
├── DiffRO (token-level, 需 Token2Text RM): 精度高, 需工程投入
├── FPO (token-selective DPO): 3-4x 数据效率, 需 error segment 标注
├── Iterative DPO (~200 pairs/round): 极低成本, 需人工介入
├── TKTO (contrastive LLM, 零配对): 6x DPO 数据效率, 仅验证发音
└── Self-reward (SASLM 路线): 零标注, 极前沿
```

**Reward Model 选择：**

```
Q3: RM 走什么架构?
├── 确定性工具组合 (WER+SIM+DNSMOS): 零成本, 覆盖有限
├── 生成式 GRM (SpeechJudge/GSRM): 全维度 CoT, 需 50K-100K 偏好数据
├── LALM 续写概率 (MCLP): 零标注, 覆盖风格一致性
├── Whisper 内部特征 (W3AR): 零标注, 覆盖对齐质量
└── 多头判别式 (UniSRM): 分维度, 需 40K 偏好数据
```

### 核心任务

| 任务 | 做什么 | 依赖 |
|------|--------|------|
| 自动评价 pipeline | 部署 Whisper(CER) + WavLM-SV(SIM) + DNSMOS + emotion2vec(SER) | 无 |
| Evaluation benchmark | 构建 500-1000 句测试集，覆盖多场景 (导航/故事/闲聊/专业) | 无 |
| GRPO baseline | 实现 GRPO: 3 维 reward (CER+SIM+DNSMOS), 8-16 rollouts, early stop 1500 步 | 评价 pipeline |
| Token2Text RM | 基于 ASR encoder 改造，支持 DiffRO | GRPO 验证后决定是否投入 |
| 偏好数据采集 | 5K-10K pairwise preference。可先用 RLAIF (LLM 自动标注) 降本 | RM 选型确定后 |
| 情感维度 reward | 加入 SER accuracy 或 MCLP 风格一致性 reward | 评价 pipeline + Instruct 方向 |
| 闭环自动化 | TTS→候选→RM 评分→筛选→训练→下一轮 | RM + post-training 方法 |

### 避坑要点

| 坑 | 怎么避 |
|-----|--------|
| 只用 CER reward → 韵律坍缩 | 至少 3 维 reward (加 SIM+DNSMOS) |
| GRPO 跑太多步 → 退化 | 严格 1500 步 early stop |
| DiffRO 温度选不好 | 退火 schedule (τ 1.0→0.5) |
| 直接合并 GRPO+DiffRO loss → 变差 | 需 sample filter 策略 |
| 全句 DPO → 信号稀释 | 用 FPO (token-selective) 或限制为 error segment |
| 优化 reward 但人听感差 | 定期人工 spot-check |

## 五、播客 / 多人对话合成 (探索方向)

### 要解决的问题

作为探索方向，核心是用最少资源建立**数据+评测+小规模验证**的能力储备。

### 路线选择

```
Q1: 技术方案?
├── Pipeline: 现有 TTS + LLM 脚本 + 拼接调度 (最快出 demo, 但跨句不连贯)
├── 复现开源: ZipVoice-Dialog (123M NAR, 全开源, RTF 0.063)
├── 在现有 AR-TTS 上改: 加 speaker-turn embedding + curriculum learning
└── 重量级: 统一 AR LM (VibeVoice/MOSS-TTSD 路线, 需 7B+, 与"不争资源"矛盾)

Q2: 帧率约束?
├── 50Hz: <30s (不可用)
├── 25Hz: ~1min
├── 12.5Hz: ~3min (FireRedTTS-2 水平)
└── 7.5Hz: ~90min (VibeVoice 水平)
→ 播客方向天然受益于效率优化方向的 12.5Hz tokenizer
```

### 核心任务

| 任务 | 做什么 | 依赖 |
|------|--------|------|
| 数据评估 | 下载 OpenDialog 6.8K hrs, 评估质量；从 Emilia 挖掘对话子集 | 无 |
| 评测 pipeline | 实现 cpWER + TTSD-eval (forced alignment 替代 diarization) | 无 |
| Benchmark 构建 | 50-100 段中英对话作为测试集 | 数据评估 |
| 小规模 PoC | Pipeline demo 或 ZipVoice-Dialog 复现，量化与 E2E 的差距 | 评测 pipeline |
| 技术路线决策 | 根据 PoC 结果决定: 继续深入 / 停在数据+评测储备 | PoC 结果 |

### 关键约束

播客时长和帧率直接挂钩。如果效率优化方向做了 12.5Hz tokenizer，播客方向自然获益，可合成 ~3min 对话。

## 六、跨方向依赖

```
                    ┌─── Instruct 扩展 (§1)
                    │       需要: 评价 + 标注数据
                    │
评价闭环 (§4) ──────┼─── Tokenizer 验证 (§3)
  (基础设施,        │       需要: 评价 (比较路线优劣)
   支撑全部)        │
                    └─── 效率优化 (§2)
                            需要: 评价 (验证不退化)

Tokenizer (§3) ──→ 效率优化 (§2): 低帧率是流式的前提
              ──→ 播客 (§5): 低帧率是长对话的前提
              ──→ Instruct (§1): 高信息密度支撑表现力

效率优化 (§2) ──→ 播客 (§5): 12.5Hz tokenizer 可共享
```

**结论**: 评价闭环是所有方向的前置基础设施；Tokenizer 是效率+播客+Instruct 三个方向的上游依赖。
