## 一、一个核心问题: 为什么 Token 设计在"辗转反复"?

### 1.1 TTS 的三个根本目标

任何 TTS 系统最终都在优化三个目标:

```
              快 (推理速度/延迟)
              △
             / \
            /   \
           /     \
          /  TTS  \
         /  系统   \
        /___________\
   稳                 好
(发音正确性)      (表现力: 韵律/情感)
```

**这三个目标天然矛盾**:
- 要"好" (表现力丰富) → 需要更多信息 → 序列更长 → 更慢, 且 AR 建模更容易出错 → 不稳
- 要"稳" (不跳字/不幻觉) → 压缩信息/简化建模 → 丢掉韵律细节 → 不好
- 要"快" (低延迟) → 序列更短/模型更小 → 信息更少 → 不好, 且可能不稳

**行业所有 Token/Codec 设计的演进, 本质上都是在这个三角内寻找不同的权衡点。**

### 1.2 演进历程: 三次转向

```
时间线:   2023 ───────── 2024 ─────────── 2025 ──────────── 2026 ──→
          
第一阶段:  声学 token (RVQ 全量)
           ├─ SoundStream, EnCodec, DAC
           ├─ VALL-E, SoundStorm
           └─ 特征: 全部信息都编进去 → "好"但不"稳"也不"快"
                     (多码本序列太长, AR 容易幻觉)

第二阶段:  语义 token (SSL/ASR 监督) + 声学分离
           ├─ CosyVoice (监督语义 token + Flow Matching 恢复声学)
           ├─ GLM-4-Voice (ASR-VQ, 175bps), Seed-TTS
           ├─ MaskGCT (SSL VQ-VAE 语义 token + 非 AR 掩码生成 + RVQ 声学补全)
           │   → 仍是语义+声学分离路线, 但生成范式从 AR 换成 mask predict
           └─ 特征: 拆分信息到不同阶段 → "稳"了, 但"好"受限
                     (语义 token 丢掉了声学细节, 靠 FM/DiT/mask 补回来)

第三阶段:  重新拥抱全量信息, 但换了建模方式
           ├─ DiSTAR (RVQ 全层 + masked diffusion, patch 级并行)
           ├─ DiTAR (连续向量预测, 不量化)
           ├─ WavTTS (直接波形 DiT, 彻底不要 codec)
           └─ 特征: 想要"好"回来, 用非 AR 方式直接建模全量信息
                     (不做语义/声学拆分, 而是在全信息空间用 patch/diffusion 生成)
```

**关键论文脉络**:
- 第一阶段的 codec 基础: [[SoundStream]] (Google, 2021) 提出 RVQ 框架 → [[DAC]] (Descript, 2023) 优化至高保真 → [[SNAC]] (Hubertx, 2024) 探索多尺度 RVQ; 对应的 TTS 系统 [[SoundStorm]] (Google, 2023) 用 mask 方式在 RVQ 上并行生成
- 第二阶段的语义 token 路线: [[CosyVoice]] (阿里, 2024) 用 ASR/TTS 多任务监督训练 tokenizer, 搭配 Flow Matching 声学渲染; [[Seed-TTS]] (字节, 2024) 定义了评估标准 (SEED-TTS-Eval); [[GLM-4-Voice]] (智谱, 2024) 走极致低码率 (175bps, 12.5Hz); [[MaskGCT]] (港中深, ICLR 2025, 210 引用) 仍用 SSL VQ-VAE 做语义 token (w2v-BERT 2.0 + VQ-VAE, 单码本 8192, 50Hz), 但将生成范式从 AR 换成非 AR 掩码预测, 证明语义 token 路线下也能脱离 AR — 它的创新在生成范式, 不在 token 设计
- 第三阶段的回归: [[DiTAR]] (字节, ICML 2025) 用 AR 预测连续向量, 不做量化; [[DiSTAR]] (X-LANCE/字节, 2025) 将 RVQ 全层 (9 层) + masked diffusion 耦合, 在全量 RVQ 码空间直接生成, 实现 patch 级并行; [[WavTTS]] (X-LANCE/字节, 2026) 跳过所有 codec 直接在波形空间建模 — 这三个系统的共同点是不做语义/声学拆分, 直接在全量信息空间建模

### 1.3 每次转向背后的逻辑

| 转向 | 面临的问题 | 解决思路 | 牺牲了什么 | 代表论文 |
|------|-----------|----------|-----------|---------|
| RVQ 全量 → 语义 token 分流 | AR 建模 RVQ 多层太难, 幻觉严重, 序列太长 | 只让 AR 建模"容易"的语义层, 声学交给另一个模型 | 表现力天花板 (语义 token 信息有限) | [[CosyVoice]], [[NaturalSpeech3]] |
| 语义 token → 重新拥抱全量 | 语义 token 丢了太多声学细节, 表现力受限; FM/DiT 补不全 | 不再拆分语义/声学, 直接在全量信息空间 (RVQ 全层/连续表征/波形) 用新范式建模 | 方案复杂度; 部分牺牲速度 | [[DiSTAR]], [[DiTAR]], [[WavTTS]] |

**核心洞察**: 

> 不是"codec 选什么"在变, 而是**"谁来承担建模难度"**在变。第一阶段让 AR 扛全部, 扛不住; 第二阶段让 codec 做预处理减轻 AR 负担, 但压缩太多; 第三阶段让新的生成范式 (diffusion/mask) 替代 AR 来扛全量信息。

### 1.4 从"codec 不考虑 TTS"到"codec 就是为了解决 TTS 问题"

**早期 codec (2022-2023)**: [[SoundStream]], EnCodec, [[DAC]] — 设计目标是**通用音频压缩**, 不考虑 TTS 建模需求。RVQ 多层、高码率、长序列, 这些特性对压缩有利, 但对 TTS 生成是灾难。[[Survey-DiscreteAudioTokens]] 系统梳理了这一阶段离散 token 的设计空间。

**现在的 codec (2025-2026)**: 设计时就在考虑"快、稳、好"的权衡:

| Codec | 设计目标 (考虑的 TTS 问题) | 权衡选择 | 出处 |
|-------|--------------------------|---------|------|
| **CosyVoice FSQ** | 稳 > 好 > 快 | 单码本+监督, 语义清晰, LM 容易学; 代价是表现力上限 | [[CosyVoice]], [[CosyVoice2]], [[CosyVoice3]] |
| **GLM 175bps** | 快 ≈ 稳 > 好 | 12.5Hz 极低帧率, 序列超短; 代价是信息量极少 | [[GLM-4-Voice]] |
| **MagiCodec** (字节) | 稳 ≈ 好 > 快 | Gaussian injection + Zipf 分布, LM-friendly; 为 LM 建模优化 token 分布 | [[MagiCodec]] |
| **SAC** (NPU/Soul) | 好 > 稳 > 快 | 双流分离 (语义+声学), 各自优化; 代价是两阶段 | [[SAC]] |
| **VARSTok** (阿里) | 快 ≈ 好 | 变长 token, 简单段落压缩多, 复杂段落保留多; 自适应 | [[VARSTok]] |
| **WavTokenizer** | 好 > 稳 | 单码本极致重建, 40 token/s; 代价是需要更强 LM | [[WavTokenizer]] |
| **无 codec** (WavTTS) | 好 >> 快/稳 | 彻底不压缩, 在波形空间建模; 代价是序列极长, 靠 DiT patch 化解决 | [[WavTTS]] |

**还有一些探索性路线**:
- **连续 VAE**: [[HoliTok]] (CUHK/阿里) 用连续表征替代离散量化, 零量化损失
- **Tokenizer-free**: [[VoxCPM]] (面壁) 用 LLM 直接建模连续语音, 跳过 tokenizer
- **多尺度融合**: [[SNAC]] 用多尺度 RVQ, [[SiTok]] (字节) 用单码本但含多尺度残差
- **跨模态设计**: [[TaDiCodec]] 用 text-aware distillation, codec 训练时就注入文本信息
- **Variable-rate**: [[FlexiCodec]] 自适应码率, 与 [[VARSTok]] 思路类似但实现不同

**结论**: Codec 设计已经从"通用音频压缩问题"变成了"TTS 建模的前置决策问题" — 你选了什么 codec, 就决定了你系统的"快、稳、好"天花板在哪里。

### 2.3 Post-training: 在三角内"微调位置"的新标配

从 2024 年字节首创 TTS RL, 到 2026 年已成行业标配 (5+ 家采用)。Post-training 不改变 codec 决定的天花板, 但在天花板内最大化效果:

| 团队 | 方法 | 优化目标 | 关键论文 |
|------|------|---------|---------|
| **字节** | RL → DPO → SpeechJudge (Reward Model) | 通用质量 (自然度+准确度) | [[SpeechJudge]] |
| **阿里通义** | DiffRO (可微分 Reward 优化) | 通用质量 (直接优化 reward, 不用 RL 近似) | [[DiffRO]] |
| **阶跃** | SFT→DPO→PPO/GRPO→RLHF (三模式) | ASR准确/TTS偏好/实时体验 | — |
| **智谱** | GRPO (四维: CER+SIM+Emotion+Laughter) | 多维度同时优化 | — |
| **Fish Audio** | GRPO (语义准确性+指令遵循+声学偏好+音色) | 开源实践 | — |

**学术前沿也在快速跟进**: [[GRPO-TTS]], [[Multi-RewardGRPO]] 探索多维度 reward 设计; [[RRPO]] 提出防 reward hacking; [[FPO]], [[MPO]], [[F5R-TTS]] 各自提出了 TTS-specific 的偏好优化变体; [[FlexiVoice]] 将 RL 用于可控性提升。

### 2.4 关键观察

**观察 1: "稳"已经不再是行业瓶颈**

2024 年, AR TTS 的幻觉/跳字/漏字是核心痛点。到 2026 年:
- 字节: Attention Guidance 基本解决 LLM-TTS 幻觉
- 我们: [[PilotTTS]] 在 SEED-TTS-Eval 上 CER/WER 最低 (CER 0.87%, WER 1.50%)
- 阿里: CosyVoice 3 的稳定性已经很好
- 多种稳定性增强方案被验证: [[TADA]] 用 CTC 对齐, [[BreezyVoice]] 用 MoE, [[RobustSpeechFlow]] 用对比 flow matching, [[StableToken]] 增强 token 抗噪性

**稳定性问题基本被解决了, 行业的竞争焦点已经转向"好"和"快"的平衡。**

**观察 2: "好"的上限取决于 token 能保留多少信息**

- CosyVoice FSQ 单码本 6561 → 信息容量有限 → 表现力天花板低
- 字节转向连续表征/多码本 → 不量化 = 不丢信息 → 表现力天花板高 ([[DiTAR]])
- [[WavTTS]] 直接波形 → 零信息损失 → 理论表现力最高

**这就是为什么字节/X-LANCE 在"绕回来"做全量信息建模 — 他们的判断是: 只要换掉 AR, 全量信息也能稳定建模。** [[DiSTAR]] 的实验证实了这一点: 0.3B 模型在 LibriSpeech 上 WER 1.66% (优于 Human 的 1.80%), 同时 CMOS +0.22 超过人类录音。

**观察 3: 架构正在多元化竞争**

SpeechLLM 领域的调研显示, 尽管 LLM backbone 已收敛到 Qwen/LLaMA 系列, 生成端收敛到 Flow Matching, 但关键分歧仍在 token 设计和建模范式:
- **AR + FM** (CosyVoice, GLM) vs **AR + DiT** (DiTAR, DiSTAR) vs **非 AR** ([[MaskGCT]], [[Metis]], [[LLaDA-TTS]]) vs **SSM** (Cartesia) vs **Dual-AR** (Fish Audio)
- 从 NLP 迁移的新范式还在不断涌入: [[LLaDA-TTS]] 将 masked diffusion LM 用于 TTS, [[Voicebox]] (Meta) 用 Flow Matching 做非 AR 填充生成

**观察 4: Post-training (RL/DPO) 是在三角内"微调位置"**

Codec 决定了你的天花板 (三角的边界), Post-training 决定了你在这个天花板内能走多远:
- [[DiffRO]]: 在 CosyVoice FSQ 的天花板内, 最大化表现力
- [[SpeechJudge]]: 在 Seed-TTS 的天花板内, 优化用户偏好
- 我们需要的: 在我们的新 token 天花板内, 对齐 instruct following

## 三、我们在哪里, 要去哪里

### 3.1 PilotTTS 的位置

[[PilotTTS]] 选择了"**稳定性优先**"的路线:

```
设计选择链:
  CosyVoice FSQ 单码本 (选了稳)
    → 语义 token, 信息有限 (牺牲了好)
      → Q-Former 隐式补 style (试图补回一些好)
        → 但隐式建模有天花板 (好的上限被 codec 决定了)
```

**结果**: 
- ✅ 稳定性 SOTA (SIM 0.862, CER 0.87%) — SEED-TTS-Eval 最高 speaker similarity
- ✅ 数据效率高 (200K h 超越百万级)  
- ✅ 多维控制 (情感 88.1%, 副语言 85.1%, 14 种方言)
- ❌ 表现力天花板受限 (Q-Former 隐式 + 单码本容量有限)
- ❌ 无上下文韵律能力

### 3.2 目标: 在三角里移动位置

```
当前位置:     稳 >> 好 > 快
       ↓
目标位置:     稳 ≈ 好 > 快      (维持稳的同时, 把"好"拉上来)
```

**关键约束**: 稳定性不能退步 (SIM > 0.85, CER < 1% 作为硬约束)。

## 四、三个规划方向 — 从"快、稳、好"三角出发

### 方向一: 提升"好"的天花板 — Token/架构重新设计

#### 核心认识

**表现力天花板由 codec/token 决定, 不是由模型大小决定的。**

2B 模型配 FSQ 单码本, 表现力不会比 0.6B 好多少 — 因为 token 能承载的信息就那么多。要真正提升"好", 必须从 token 层面解决。

这一判断有实证支撑: [[NaturalSpeech3]] 最早提出语义-声学分解 (FACodec), 发现将韵律/内容/音色拆开各自建模能显著提升表现力; [[SAC]] 进一步将双流设计简化为语义流+声学流独立优化; [[MBCodec]] 也探索了多频带分解的路线。

#### 可选路线 (从"快、稳、好"三角分析)

| 方案 | 对"好"的提升 | 对"稳"的风险 | 对"快"的影响 | 代表论文 | 适合我们吗 |
|------|------------|------------|------------|---------|-----------|
| **双流 (语义+声学)** | 高 — 声学流保留细节 | 低 — 语义流仍负责稳定 | 中 — 两阶段但可并行 | [[SAC]], [[NaturalSpeech3]] | ★★★★★ 最平衡 |
| **多码本 RVQ + 非 AR 生成** | 很高 — 全量信息 | 中 — 非 AR 稳定性待验证 | 低 — patch 并行可缓解 | [[DiSTAR]], [[SoundStorm]] | ★★★★ 潜力高但风险大 |
| **连续表征 (不量化)** | 最高 — 零量化损失 | 中 — AR 建模连续值更难 | 中 | [[DiTAR]], [[VoxCPM]], [[HoliTok]] | ★★★ 字节在做, 我们跟进成本高 |
| **单码本扩容 (更大 codebook)** | 中 — 容量提升有限 | 低 — 最保守 | 快 — 序列不变 | [[WavTokenizer]], [[SiTok]] | ★★★ 收益有限但风险最低 |
| **变长 token** | 高 — 自适应保留信息 | 中 — 变长对 AR 是挑战 | 高 — 简单段落可很短 | [[VARSTok]], [[FlexiCodec]] | ★★★★ 蓝海, 学术价值高 |

**建议路线**:

```
短期 (验证期):  保持 FSQ 单码本, 升级模型到 2B
               → 确认"好的上限确实是 codec 而不是模型"
中期 (突破期):  探索双流 codec (语义流保稳定 + 声学流提表现力)
               → 这是"稳"和"好"兼得的最佳候选
长期 (差异化): 如果变长 token 验证可行 → 高学术价值
```

#### 架构层面的配合

Token 升级需要架构配合:

| 架构升级 | 目的 | 参考 |
|----------|------|------|
| 模型规模 → 2B | 充分利用新 token 的信息容量 | [[CosyVoice3]] (1.5B), [[Qwen3-TTS]] |
| 多阶段训练 | 低质量大规模 PT + 精选 CT + RL | 行业共识 (CosyVoice 3, Qwen3-TTS) |
| 显式 Style Module | 替代 Q-Former 隐式建模, 直接预测韵律属性 | [[EmoCtrl-TTS]] (训练免显式控制), [[HierarchicalEmotionControl]] (分层情感) |
| LLM 权重初始化 | 加速收敛, 降低训练成本 | [[Qwen3-TTS]], [[GLM-4-Voice]] |

### 方向二: In-context 韵律 — 从单句建模到上下文建模

#### 核心认识

**"快、稳、好"的三角, 在加入上下文之后变成了四面体:**

```
              快
              △
             /|\
            / | \
           /  |  \
          / 上下文 \      ← 新维度: 跨句一致性/连贯性
         /_________|
     稳              好
```

上下文韵律不只是"更好听", 而是一个独立的能力维度:
- 同一情感设定下, 多句话的情感不退化 (Style Amnesia 问题)
- 对话中的语调呼应 (A 问得急, B 回答也加速)
- 段落级"朗读感" (起承转合的韵律结构)

#### 行业现状: 几乎空白

几乎没有系统在做:
- Sesame CSM 做了"对话韵律" (Voice Presence) — 但仅英语, 且效果有限
- ElevenLabs 的 Conversational AI 有隐式 context — 但完全闭源
- 学术上刚开始探索: [[TextAwareContextAwareTTS]] 用文本上下文指导韵律; [[BorderlessLongSpeech]] 做跨句情感弧线建模; [[Audiobook-CC]] 构建了有声书级的上下文标注数据集

行业全景调研也确认了这一空白: 在 30+ 团队中, "对话韵律建模"和"长文本一致性 (> 10 分钟)" 被列为最大的技术空白领域。

#### 两个子问题

**子问题 1: 单句内的表现力 (当前焦点)**

这是大多数系统在做的 — 单句合成要好听。PilotTTS 的情感/副语言控制属于这层。学术上有丰富的工作: [[EmoCtrl-TTS]] 做训练免的情感控制, [[EmoSteer-TTS]] 用梯度引导调整情感, [[HierarchicalEmotionControl]] 做分层级的情感控制。

**子问题 2: 跨句的上下文韵律 (行业空白)**

- 学术上刚起步: [[TextAwareContextAwareTTS]] 证明文本上下文能改善韵律; [[BorderlessLongSpeech]] 做了跨句情感弧线
- 评测几乎空白: NTU 的 Full-Duplex-Bench 只评测了 turn-taking, 不评韵律连贯
- 数据稀缺: [[Audiobook-CC]] 构建的有声书数据集是少有的上下文标注资源

#### 需要的资源

| 资源 | 说明 | 优先级 |
|------|------|--------|
| **Context 数据** | 段落级有声书 (有"朗读感"), 对话播客 (有韵律呼应) | P0 |
| **高表现力标注工具** | 不是标 word-level, 而是标 sentence-to-sentence 的韵律变化模式 | P0 |
| **多人重叠检测** | 真实对话中 10-20% 是 overlap, 需要分离和建模 | P1 |
| **对话级评测** | 评估跨句一致性, 现有评测全是单句的 | P1 |

#### 技术方案思考

| 层面 | 方案 | 说明 |
|------|------|------|
| **数据** | 段落/对话数据采集 + 句间关系标注 | 标注"这两句之间的韵律关系是什么"; 可参考 [[Audiobook-CC]] 的标注方案 |
| **模型** | 扩展 AR context window, 输入前几句的 hidden state | 最直接, 工程量可控 |
| **规划** | Segment-level prosody planning (先规划后执行) | 类似 LLM 的 CoT |
| **评估** | 构建对话/段落级评测集 | 目前行业无标准; 可参考 NTU Full-Duplex-Bench 思路扩展 |

### 方向三: 语音属性评价 & 标注 & 强化 — 优化闭环

#### 核心认识

**"快、稳、好"三角里, "稳"和"快"是可量化的 (CER/WER, TTFB/RTF), 但"好"是主观的、多维度的、缺乏闭环的。**

```
快: TTFB (ms), RTF → 可精确测量 → 可直接优化
稳: CER (%), WER (%), SIM → 可精确测量 → 可直接优化
好: ??? → MOS (1-5分, 粗糙) → 无法有效引导优化
```

所有团队的 RL/DPO 都在优化"稳" (CER/SIM) 或粗粒度的"好" (MOS/偏好), **没有团队在做细粒度的"好"的度量和优化** — 特别是 "instruct following: 你让它说得开心, 它到底开心了没有?"

#### 评价现状: 工具在涌现但缺乏闭环

学术界已经有一批评价工具出现, 但各自独立, 未形成优化闭环:

| 评价工具 | 评价什么 | 局限 | 出处 |
|----------|---------|------|------|
| [[SpeechJudge]] (字节) | 通用质量 (基于 Qwen2.5-Omni-7B) | 不做 instruct following | 字节内部 → 论文 |
| [[TTS-PRISM]] (小米/清华) | 12 维诊断评分 | 诊断但不优化 | 学术 |
| [[InstructTTSEval]] | Instruct following 评测集 | 只有评测, 无 RM | 刚出现 |
| [[ProsodyEval]] (字节) | 韵律维度评估 | 粒度较粗 | 字节内部 |
| [[Vox-Evaluator]] | 多维度自动评估 | 通用, 不针对 TTS 控制 | 学术 |
| [[UniSRM]], [[GSRM]] | 统一语音 Reward Model | 通用 reward, 不做属性对齐 | 学术 |

**关键 gap**: 评"通用好不好" (SpeechJudge, UniSRM) 的工具有了, 但评"控制指令是否被遵循" (instruct following) 的工具几乎没有。[[InstructTTSEval]] 是唯一一个, 但只有评测集, 没有训练好的 Reward Model。

#### 分层级标注体系

设计一套从粗到细的标注维度:

```
第一层 (基础属性):   情感类别, 语速 (syllable/sec), 平均音高, 能量
                    → 自动化提取, 零人工成本
                    
第二层 (动态属性):   音高轮廓形状, 停顿模式, 语速变化曲线, 重音分布
                    → 半自动 (工具提取 + 人工校验)
                    
第三层 (主观属性):   自然度, 表现力, 情感强度 (连续值), 适当性
                    → 需要人工标注, 可用 LLM-as-Judge 辅助
                    
第四层 (偏好关系):   A > B 在哪个维度好? 
                    → 成对比较, 多维度打分
```

**关键**: 第二层和第三层之间有一个 gap — 物理可测量的属性 (F0/duration/energy) 和主观感知 (好听/有感情) 之间的映射关系不清楚。**这个映射本身就是 Reward Model 要学的东西。** [[NoVerifiableRewardforProsody]] 深入讨论了韵律优化中 reward 难以验证的问题, 是这个方向的理论基础。

#### Reward Model: 从"好不好"到"哪里好/哪里不好"

| RM 类型 | 输入 | 输出 | 用途 | 参考 |
|---------|------|------|------|------|
| **Instruct-Following RM** | (指令, 音频) | 遵循度分数 | "说快点"→ 真的变快了吗 | [[InstructTTSEval]] (评测思路) |
| **属性级 RM** | (音频, 目标属性) | 属性匹配度 | 目标情感=开心 → 多开心? | [[FlexiVoice]] (属性控制+RL) |
| **偏好 RM** | (音频A, 音频B) | 偏好概率 | 哪个更好 + 为什么 | [[SpeechJudge]], [[DiffRO]] |
| **诊断 RM** | 音频 | 多维度评分 + 问题定位 | 类似 [[TTS-PRISM]] 12 维诊断 | [[TTS-PRISM]] |

#### 强化闭环

```
分层标注 → 训练 RM → RL/DPO 优化 → 更好的 TTS → 生成新样本 → 标注 → ...
                                                    ↑
                                        TTS Edit 数据飞轮
                                   (情感编辑/韵律编辑扩充标注数据)
```

已有的 RL 方法可以直接适配:
- [[GRPO-TTS]], [[Multi-RewardGRPO]]: 多维度 GRPO, 可用于多属性同时优化
- [[RRPO]]: 防 reward hacking, 保证 RL 不退化
- [[DiffRO]]: 可微分 reward, 如果有可微的属性评估器可直接使用
- [[FPO]], [[MPO]], [[F5R-TTS]]: 各种 TTS-specific 偏好优化变体

**与行业的差异化**: 
- 行业做的是: "通用质量 RL" (让 TTS 整体更好听)
- 我们要做的是: "属性对齐 RL" (让 TTS 精确遵循指定的属性控制)

## 五、三个方向在"快、稳、好"三角中的作用

```
方向一 (Token/架构)   → 扩大三角的边界 (提升"好"的天花板)
方向二 (In-context)   → 增加一个维度 (从三角变四面体)
方向三 (评价/强化)    → 在边界内精准移动位置 (用 RL 最大化当前天花板下的"好")
```

优先级:
1. **方向一是前提**: Token 不升级, "好"的天花板就在那里, RL 再怎么优化也超不过
2. **方向三和方向一并行**: RL 工具链可以在旧 token 上先验证, 新 token 出来后直接用
3. **方向二在方向一成熟后自然扩展**: 单句的表现力够了, 再考虑跨句

```
                    ┌─────────────────────────────────────────┐
                    │  方向三: 评价 & 标注 & 强化 (闭环工具)    │
                    │  "怎么衡量好不好, 怎么变得更好"            │
                    └──────────┬──────────────┬───────────────┘
                               │              │
                    Reward 信号 ↓              ↓ 数据标注
                    ┌──────────┴──┐    ┌──────┴───────────┐
                    │ 方向一:       │    │ 方向二:            │
                    │ Token/架构   │    │ In-context 韵律   │
                    │ (天花板提升)  │    │ (场景扩展)         │
                    └─────────────┘    └──────────────────┘
```

## 六、总结: 从 Codec 演进看我们的位置和机会

### 行业的本质叙事

```
2023:  Codec 是"通用音频压缩" → TTS 被迫适配 → 各种问题
       (SoundStream, EnCodec, DAC)
2024:  发现问题, 开始为 TTS 设计 codec → 语义 token 崛起 → 稳了但表现力受限
       (CosyVoice, Seed-TTS, GLM-4-Voice)
2025:  稳定性基本解决, 表现力成新瓶颈 → 重新拥抱全量信息 + 新生成范式
       (DiTAR, DiSTAR, MaskGCT, WavTokenizer, SAC)
2026:  分化: 各家选不同的"快/稳/好"权衡点 → 差异化来自"你选了什么权衡"
       (WavTTS, VARSTok, VoxCPM, CosyVoice 3 + DiffRO)
```

### 我们的机会

**我们已经拿到了"稳"的先发优势 (PilotTTS SIM SOTA)。** 行业已经过了"稳"是核心瓶颈的阶段。

下一步的竞争焦点是"好" — 但不是无差别的"好", 而是**可控的"好"**: 我让它怎么表达, 它就怎么表达, 而且我能度量它做得对不对。

```
我们的差异化:

  通用表现力 (字节/阿里在追求的)     可控表现力 (我们要做的)
  ─────────────────────────       ─────────────────────────
  "随机地好听"                      "精确地好听"
  "不知道为什么好"                   "知道为什么好, 能复现"
  "评估靠 MOS"                     "评估靠属性匹配度"
  "RL 目标: 通用偏好"               "RL 目标: instruct following"
```

### 一句话

> **从 codec 演进看, 行业正在从"为稳定性压缩信息"转向"用新范式建模全量信息"。我们的策略是: 在升级 token 提升表现力天花板的同时, 建立"属性评价→标注→强化"的闭环, 做到可控的表现力 — 不是随机地好, 而是精确地好。**
