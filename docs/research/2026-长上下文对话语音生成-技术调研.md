# 长上下文对话语音生成 — 技术调研与规划

> 调研日期: 2026-06-12
> 目的: 回答两个问题 — (1) 如何使 TTS 在长上下文对话中生成自然、拟人的语音 (2) 如何评价长上下文语音生成的质量
> 产品参照: Google NotebookLM Audio Overview — 自动将文档转化为两人自然对话播客,具备犹豫、打断、追问、共情等拟人特征

---

## 一、问题定义

### 1.1 什么是"长上下文对话语音的自然性"

传统 TTS 优化的是 **单句质量** — 给一句文本,生成一段清晰、自然的语音。但在对话场景中,自然性不止于单句:

| 维度 | 单句 TTS | 长上下文对话 TTS |
|------|---------|----------------|
| 韵律 | 单句内合理 | 跨句连贯,与对话节奏匹配 |
| 情感 | 固定标签或无 | 随对话发展动态变化 |
| 语气 | 统一 | 追问/感叹/犹豫/回应各不同 |
| 停顿 | 句内自然 | 句间节奏与 turn-taking 拟人 |
| 副语言 | 无 | 嗯/啊/笑声等 backchannel |
| 说话人交互 | N/A | 接话、打断、共情回应 |

**核心定义**: 在多轮对话上下文中,TTS 自动推断每句话合适的情感、语气、韵律、副语言,使整体对话听起来像真人对话而非逐句朗读拼接。

### 1.2 核心论点: 上下文是实现拟人自然的路径

"拟人、自然"是抽象目标。将其拆解,实现路径是 **引入更多上下文 (显式或隐式),让合成语音具备更丰富且合理的情感和韵律**。

这里"丰富"和"合理"是两个正交的维度:

| | 丰富度低 (平淡) | 丰富度高 (有表现力) |
|---|---|---|
| **合理性低** (不看上下文) | 当前 VoiceAgent 现状: 默认语气朗读,安全但机械 | **更差**: 随机加情感,用户投诉时 Agent 欢快回应 |
| **合理性高** (理解上下文) | 不现实: 理解了上下文却不表达 | **目标**: 在对的时机用对的语气 |

关键洞察: **没有上下文的"丰富"比"平淡"更危险。** 当前 Instruct 模型已具备表现力 (丰富度),缺的是上下文驱动的合理性。上下文的作用不是让语音"更有表现力",而是让表现力**发生在对的地方**。

这也决定了评估的核心方向: 不是评"表现力够不够丰富",而是评"表现力是否与上下文匹配"。

**进一步区分: 演绎式情感 vs 对话式语气**

VoiceAgent 需要的不是"表演开心/悲伤"这样的演绎式情感,而是对话中微妙的语气调整 — "温和一点""坚定一点""放慢一点":

| 维度 | 演绎式情感 | 对话式语气 |
|------|----------|----------|
| 表现形式 | happy/sad/angry,明显可辨 | 温和/坚定/耐心/轻松,微妙连续 |
| 粒度 | 离散类别 | 连续程度差异 |
| 判断依据 | 单句可判断 | 需要上下文才知道是否合适 |
| 标注数据 | 丰富 (IEMOCAP/ESD) | 几乎没有 |
| 评估方式 | SER 分类器可自动评 | 分类器无法覆盖,需要新方案 |

这个区分直接影响评估设计: 基于情感分类器的评估 (如 emotion accuracy) 对演绎式情感有效,但对对话式语气几乎无效 — 分类器大概率把"稍微温和一点"和"稍微坚定一点"都识别为 neutral。评估方案必须绕开离散分类,转向连续的合理性判断 (见 Section 7.4)。

**渐进策略: 表现力与评估能力同步扩展**

空谈丰富度无意义 — 脱离上下文的丰富度无法评估,也不应追求。务实路径是从易评估的离散风格起步,逐步扩展:

| 阶段 | 表现力范围 | 评估方式 | 可行性 |
|------|----------|---------|--------|
| **Phase 1** | 5-8 个高频离散风格 (开心/安慰/讲故事/客服/笑声/严肃) | SER 分类器 + 上下文匹配准确率 | 现有工具直接可做 |
| **Phase 2** | 扩展到自然语言描述 ("温和但坚定地") | LALM-as-Judge + 对比偏好 | 需要验证 LALM 相关性 |
| **Phase 3** | 隐式上下文推断,不需要显式描述 | 对话级 RM + 人类偏好数据 | 需要建数据+训模型 |

Phase 1 的类别选择标准: **(1) 高频** — VoiceAgent 场景中真正常用; **(2) 可评** — 现有分类器能区分; **(3) 有上下文依据** — 什么场景该用什么风格有共识。Phase 1 做实后,Phase 2/3 自然知道哪些维度值得扩展、什么粒度的控制足够。

### 1.3 与相邻方向的区分

- **vs Instruct TTS**: 不需要逐句给 style instruction,"context is the instruction"
- **vs Full-duplex/Omni**: 不追求端到端实时交互,聚焦离线/近线的对话语音生成质量
- **vs Emotion TTS**: 不是固定 N 类分类,而是上下文决定的连续表达空间
- **vs 零样本克隆**: 说话人音色只是基线能力,核心挑战是跨句的表达连贯性

### 1.4 产品参照: NotebookLM Audio Overview

Google NotebookLM 的 Audio Overview 是当前最成功的长上下文对话语音产品:
- 将用户上传的文档自动转化为 ~10 分钟的双人自然播客
- 两个"主持人"自然讨论文档内容,具备追问、打断、犹豫、共情等交互特征
- 用户反馈核心卖点不是单句音质,而是"对话感" — 两人之间的自然互动

**技术推测** (基于公开信息、DeepMind 博客、Latent.Space 访谈等,Google 未官方确认完整技术栈):
- **脚本生成**: Gemini 1.5/2.0 Pro 基于用户上传文档生成对话脚本,包含内容组织、追问点、情感标记
- **语音合成**: 社区共识 (Google AI 开发者论坛 accepted answer) 指向 **SoundStorm** 衍生模型 — Google 的 MaskGIT 并行解码架构,可在 AudioLM semantic tokens 基础上快速生成高质量多说话人语音。关键技术细节:
  - **自定义 codec**: ~600 bps 码率,分层 token 结构 (粗粒度语义 + 细粒度声学)
  - **速度**: 2 分钟音频在 TPU v5e 上 <3 秒生成
  - **副语言生成**: 犹豫词 (um, uh)、笑声等 disfluencies 由 **音频模型自身** 生成,而非脚本层面注入 — 这是对话自然度的关键技术点
  - **安全**: SynthID 音频水印,嵌入生成过程
- **对话自然度关键**: 用户反馈认为不是简单的"两段 TTS 拼接",而是整体对话感 — 语速变化、强调、语调起伏、自然的 turn-taking 节奏。disfluencies 在音频层而非脚本层生成,意味着模型学会了"在哪里犹豫/在哪里笑"的对话韵律模式
- **技术栈推测**: Gemini (脚本+上下文理解) → 对话编排 (内容/节奏/情感标记) → SoundStorm 衍生模型 (语音合成 + 副语言生成) → 后处理 (混音/节奏调整)
- **2025 年 I/O 更新**: Gemini 2.5 Flash 获得原生音频输出能力,NotebookLM 底层可能已迁移; NotebookLM Studio 扩展了音频能力,支持更多自定义

这个产品定义了方向的核心价值: **上下文理解驱动的对话韵律自然性**。两个关键启示: (1) 对话语音的"自然感"可能更多来自脚本层面的对话设计 (何时追问、何时犹豫、何时共情); (2) 副语言 (disfluencies) 应由音频模型隐式学习而非显式脚本标注,这与 Pattern C (端到端隐式) 的技术判断一致。

## 二、技术路线分析: 怎么生成

### 2.1 四种技术 Pattern

#### Pattern A: LLM 作为外部风格推断器
```
对话上下文 → LLM 推断 emotion/style/prosody → style token/tag → TTS 条件渲染
```

| 系统 | 年份/会议 | 做法 | 优劣 |
|------|----------|------|------|
| ConversationalTTS-RL | 2026, Amazon | LLaMA 3 70B 生成 style token → AR prosody model + RL(AES-CE reward) | 首个 ICL+RL 耦合; 解耦 prosody-timbre |
| CapTalk | 2026 | CoT 规划 turn-level emotion/tone/pitch/energy/speed → FHVAE 解耦 | 层次化变分条件; 对话 SIM 0.808 |
| Chain-Talker | 2025, ACL | 三阶段认知: 情感理解→语义理解→共情渲染 | 首次 CoT 式 CSS |
| JELLY | 2025, ICASSP | LLM + multi-LoRA 联合情感+推理 | 轻量适配 |
| ChatGPT-EDSS | 2023 | ChatGPT 提取意图/情感词 → TTS | 最早的 LLM-CSS 组合 |

**优势**: 可解释性强,LLM 的推理链可审计
**劣势**: 级联延迟,LLM 推断 + TTS 生成两步; 依赖 LLM 风格描述的准确性

#### Pattern B: 专用上下文编码器
```
对话历史 (text + audio) → 图/Transformer 编码器 → style vector → TTS decoder
```

| 系统 | 年份/会议 | 做法 | 优劣 |
|------|----------|------|------|
| MFCIG-CSS | 2025, EMNLP | 双图: 语义交互图(SIG) + 韵律交互图(PIG), 首次词级交互 | 粒度最细 |
| DiffCSS | 2025, 清华 | Diffusion prosody predictor + 对话上下文条件 | 解决 one-to-many |
| RADKA-CSS | 2025, Rui Liu | RAG 检索相似历史对话 + 异构图聚合 | 引入外部知识 |
| ECSS | 2024, AAAI | 异构图建模对话情感流 + 对比学习 | CSS 情感建模开创 |
| TextAware-ContextAware | 2024, Interspeech | CLIP 对比学习从文本预测 style embedding + 跨句 context encoder | 有声书韵律 |

**优势**: 模块化,可插拔到现有 TTS 系统
**劣势**: backbone 普遍偏旧 (FastSpeech 2 / VITS),与 LLM-TTS 架构不兼容; 数据集小 (DailyTalk ~20h)

#### Pattern C: 端到端隐式 (LLM 自身学会)
```
多轮 text-speech interleaved tokens → LLM → 自动带风格的语音 tokens
```

| 系统 | 年份 | 做法 | 优劣 |
|------|------|------|------|
| VibeVoice | 2025, 微软 | Qwen2.5 + dual tokenizer (acoustic+semantic), 90min/4spk, curriculum 4K→64K | 最长上下文; 超越 ElevenLabs/Gemini |
| MOSS-TTSD | 2026, 复旦 | Qwen3-8B + 16层 RVQ, 60min/5spk, voice_clone+continuation 融合 | 最多说话人; TTSD-eval |
| FireRedTTS 2 | 2025, 小红书 | Qwen2.5 dual-transformer, text-speech interleaved, 3min/4spk | 从显式标签→隐式上下文推断 |
| DialoSpeech | 2025, NPU | LLaMA + dual-track semantic tokens + chunked CFM | 双轨建模重叠/静默 |
| CSM | 2025, Sesame | Llama + Mimi codec, "Voice Presence" 对话韵律 | 14.7K stars, 纯上下文隐式 |
| JoyVoice | 2025, 京东 | Qwen2.5-0.5B + Global Causal DiT, 8spk/5min | E2E 联合训练 |
| ZipVoice-Dialog | 2025, 小米 | Zipformer + CFM (NAR), curriculum + speaker-turn embedding | 首个 NAR 对话生成 |
| SASLM | 2026, EMNLP sub | 3B SLM + VIB 自蒸馏 intent + self-reward 对齐 | 无需任何情感标注 |

**优势**: 无级联,上下文信息自然流入; 可扩展到长序列; 与 LLM-TTS 趋势一致
**劣势**: 黑盒,不可解释"为什么这样读"; 需要大量对话训练数据; 长上下文训练成本高

#### Pattern D: RAG 增强
```
当前对话 + 检索相似历史对话 → 风格参考聚合 → TTS
```
- RADKA-CSS (2025): RAG + 异构图
- AutoStyle-TTS (2025): LLM embedding 匹配风格 prompt

### 2.2 核心技术问题

#### (1) 长序列建模
最核心的工程挑战。3 分钟对话在 12.5Hz 下约 2250 token,加上文本约 3K-5K token; 90 分钟则需要 64K+ token。

| 系统 | 最大长度 | 帧率 | 解决方案 |
|------|---------|------|----------|
| VibeVoice | 90 min | 7.5 Hz | 极低帧率 + curriculum 4K→64K |
| MOSS-TTSD | 60 min | 12.5 Hz | Qwen3 65K 上下文 + 三阶段 curriculum |
| FireRedTTS 2 | 3 min | 12.5 Hz | Dual-transformer (backbone + decoder) |
| DialoSpeech | ~1 min | 25 Hz | Chunked FM + block-wise guided attention |
| JoyVoice | 5 min | 12.5 Hz | Random chunk 训练统一流式/非流式 |

**关键 takeaway**: 低帧率 (7.5-12.5 Hz) + curriculum 长度增长是当前最有效的长序列方案。

#### (2) 说话人一致性与切换
多说话人对话中,音色必须在长时间跨度内保持稳定,同时 turn-taking 要自然。

| 方案 | 代表 | 做法 |
|------|------|------|
| Speaker tag + interleaved | FireRedTTS 2, MOSS-TTSD | [S1]text+speech[S2]text+speech... |
| Dual-track | DialoSpeech | 两条并行 token 流,各自独立 |
| Speaker embedding conditioning | JoyVoice | ECAPA-TDNN 嵌入 |
| Learnable turn embedding | ZipVoice-Dialog | 可学习说话人-轮次嵌入 |
| Voice clone + continuation | MOSS-TTSD | 前几秒 clone + 后续 continuation |

#### (3) 上下文韵律推断
核心创新点 — 如何从对话上下文推断当前句的韵律。

| 方法 | 代表 | 上下文信息 | 推断方式 |
|------|------|-----------|---------|
| 文本历史 → 图编码 | MFCIG-CSS, ECSS | 前几轮文本 | GNN/GraphSAGE |
| 文本历史 → LLM 推理 | ConversationalTTS-RL, Chain-Talker | 前几轮文本 | LLM CoT |
| 文本+音频历史 → LLM 隐式 | VibeVoice, MOSS-TTSD | 前文 text-speech interleaved | LLM attention 自动提取 |
| 音频历史 → VIB 自蒸馏 | SASLM | 前几轮音频 | VIB 信息瓶颈 |
| 音频历史 → Diffusion | DiffCSS | 前几轮音频韵律 | Diffusion 多样采样 |

#### (4) 对话数据的获取与处理
**核心瓶颈**: 高质量多通道对话数据极度稀缺。

| 数据策略 | 代表 | 做法 |
|---------|------|------|
| 公开对话数据集 | DailyTalk (~20h), NCSSD (236h) | 规模小、多为表演性 |
| 自建 pipeline | DialoSpeech | VAD+ASR+diarization+OSD+separation |
| 合成拼接 | MOSS-TTSD, JoyVoice | 单人数据按脚本拼接 |
| 单声道分离 | FireRedTTS 2 | 播客音频源分离 |
| Curriculum 策略 | 几乎所有系统 | 单人→双人→多人渐进训练 |
| 新数据集构建 | ZipVoice-Dialog (OpenDialog 6.8Kh) | 首个大规模开源对话 TTS 数据 |

**所有系统的共同结论: 数据是这个方向的最大瓶颈,方法创新几乎都是在绕过数据不足。**

### 2.3 技术路线判断

| 维度 | Pattern A (LLM推断) | Pattern B (专用编码器) | Pattern C (端到端隐式) |
|------|-------------------|---------------------|---------------------|
| 可扩展性 | 中 (依赖 LLM) | 低 (图结构固定) | 高 (随 LLM 扩展) |
| 可解释性 | 高 (CoT 可审计) | 中 (embedding 可视化) | 低 (黑盒) |
| 长度支持 | 无限 (LLM 推理) | 短 (~10 轮) | 长 (64K+ token) |
| 与现有 TTS 架构兼容 | 高 (插件式) | 低 (backbone 老旧) | 高 (LLM-TTS 原生) |
| 数据需求 | 低 (LLM 零样本) | 中 (需对话韵律标注) | 高 (大量对话音频) |
| 产业采用 | 少 | 无 | **多** (VibeVoice/MOSS-TTSD/FireRedTTS2) |

**结论**: Pattern C (端到端隐式) 是工业界主流选择,与 LLM-based TTS 的大趋势一致。Pattern A (LLM推断) 是有价值的补充,尤其在数据不足时可作为冷启动方案。Pattern B 的学术窗口正在关闭。

## 三、评价体系: 怎么评

### 3.1 现有评估方法及其在对话场景的局限

#### 单句级指标 (现状)

| 指标 | 评价维度 | 对话场景局限 |
|------|---------|-------------|
| MOS | 主观自然度 | 逐句评分,无法衡量跨句连贯性 |
| WER/CER | 内容准确性 | 不反映韵律/情感质量 |
| SIM | 音色相似度 | 不衡量表达力和上下文适配 |
| UTMOS | 自动 MOS 预测 | 在单句上训练,对上下文不敏感 |
| F0/Energy/Duration | 韵律客观 | 无"合理性"判断,只有统计距离 |

**核心问题**: 所有主流指标都在 **单句粒度** 上定义,无法回答"这段对话整体听起来自然吗?"

#### 已有的对话级评估尝试

| 评估方法 | 提出者 | 维度 | 局限 |
|---------|-------|------|------|
| **TTSD-eval** | MOSS-TTSD (复旦, 2026) | 基于 forced alignment 的多说话人评估,避免 diarization 误差; 指标: ACC (说话人准确率) + SIM + WER | 仅评估基础质量,不评估对话自然度/韵律连贯性 |
| **cpWER/cpSIM** | ZipVoice-Dialog (小米, 2025) | concatenated minimum-permutation WER/SIM: 自动匹配最优说话人排列 | 解决了多说话人评估的说话人映射问题,但仍是单句指标的聚合 |
| **Spontaneity MOS** | DialoSpeech (NPU, 2025) | 人工评估对话自发性 (3.96 vs CosyVoice2 3.44) | 主观,不可自动化 |
| **Context Coherence** | CapTalk (2026) | 人工评估上下文连贯性 (4.18) | 主观,仅 CapTalk 一家使用 |
| **EchoMind** | ICLR 2026 | 共情 SLM benchmark: 语音感知→推理→生成 | 侧重共情/情感,非对话韵律全面评估 |

### 3.2 多维评估框架 (已有参考)

#### SpokenDialogueEvaluation 11 维框架 (WavChat Survey)

WavChat 提出的 11 维两级评估体系:

**Basic Level:**
1. Text Intelligence — 语义内容质量
2. Speech Quality — MOS + WER
3. Streaming Latency — TTFB + RTF

**Advanced Level:**
4. Speech Intelligence — 副语言理解与生成 (情感/语气/口音)
5. Audio Understanding & Generation — 非语音音频
6. Multilingual — 多语言
7. Context — 多轮对话上下文利用
8. Interaction — Turn-taking / 打断 / Backchannel
9. Safety
10. Fairness
11. Robustness

**问题**: 框架全面但过于通用,缺少针对 "长上下文对话 TTS" 的具体可操作指标。

#### TTS-PRISM 12 维诊断框架 (小米+清华, 2026)

针对中文 TTS 的 12 维分层评估:
- 通过 MiMo-Audio-7B 实现单次推理的多维评分 + 可解释推理
- 每维先生成 rationale 再打分
- 12 维平均 LCC 0.717 / SRCC 0.721

**问题**: 12 维聚焦单句声学质量 (发音/韵律/音色等),不包含跨句/对话级维度。

#### SpeechJudge (字节, 2025)

- 99K pairwise 人类偏好数据 + GRM reward model
- 聚焦 naturalness preference
- 可用于 TTS post-training

**问题**: 仅覆盖单句 naturalness,不涉及对话上下文。

#### PodEval (EMNLP 2025) — 首个播客评估框架

**最相关的已有评估工作**。PodEval 是首个系统化的播客音频评估框架:
- 评估维度: Content Quality (信息准确/逻辑) + Audio Quality (音质/韵律) + Podcast Quality (对话交互/自然度)
- 从"播客整体体验"出发评估,而非单句
- 设计了三层评估: 自动指标 + LALM-as-Judge + 人工评估协议

**与本方向的关系**: PodEval 是当前最接近"对话级 TTS 评估"的框架。但其侧重评估播客内容质量 (脚本层面),对对话语音韵律的评估粒度不够细 — 未区分跨句韵律连贯性、情感轨迹、turn-taking 节奏等子维度。

#### SwanBench-Speech (ACL Findings 2026) — 多场景语音生成基准

- 1,101 测试样本,覆盖 17 个场景 (含对话、播客、有声书等)
- 使用 LALM-as-Judge 自动评估
- 覆盖面广,但每个场景深度有限

**与本方向的关系**: SwanBench 覆盖了对话/播客场景,但作为通用 benchmark 未深入长上下文对话的特有挑战。可作为补充基准但不能替代专用评估。

#### PodBench (2026) — 播客脚本生成评估

- 侧重评估 LLM 生成的播客脚本质量
- 覆盖内容组织、对话结构、追问设计等

**与本方向的关系**: 评估的是脚本层面,不直接评估语音质量。但脚本质量 (何时追问、何时犹豫) 是对话自然度的前提,可参考其评估维度设计。

### 3.3 长上下文对话 TTS 评估的缺失维度

基于对现有方法的分析,当前评估体系在以下维度完全缺失:

| # | 缺失维度 | 定义 | 为什么重要 |
|---|---------|------|-----------|
| 1 | **跨句韵律连贯性** | 前后句韵律过渡是否自然 | 逐句合成的核心问题:句间韵律跳变 |
| 2 | **情感轨迹一致性** | 对话中情感变化是否合理 | 情感突变 (突然开心→突然悲伤) 不自然 |
| 3 | **Turn-taking 自然度** | 说话人切换的时机和节奏 | 间隔太长像朗读拼接,太短像打断 |
| 4 | **副语言适当性** | 嗯/啊/笑声/叹气的位置和频率 | 有→拟人,无→机器感,过多→做作 |
| 5 | **说话人一致性 (长时)** | 同一说话人在对话全程的音色稳定性 | 短对话不暴露,长对话可能漂移 |
| 6 | **内容-语气匹配** | 语气是否与所说内容匹配 | 严肃内容用轻松语气不自然 |
| 7 | **对话节奏整体感** | 整段对话的快慢节奏是否合理 | 非均匀节奏才自然:重点慢,过渡快 |
| 8 | **Listener 响应自然度** | 听者的回应是否符合语境 | "嗯"/"对"的时机和语气 |

### 3.4 建议的评估框架

#### 层级 1: 基础质量 (沿用现有指标)
- **内容准确**: cpWER/cpCER (已有)
- **音色保持**: cpSIM (已有)
- **单句自然度**: UTMOS / MOS (已有)

#### 层级 2: 对话质量 (新增)
- **韵律连贯性**: 相邻句 F0/energy/speed 变化的合理性评估
  - 可操作方案: 训练 prosody coherence classifier,区分真实对话 vs 随机句拼接
- **情感一致性**: 对话中情感标签序列的合理性
  - 可操作方案: 对每句做情感识别,判断情感序列是否符合对话逻辑
- **Turn-taking 自然度**: 说话人切换间隔的分布与真实对话的距离
  - 可操作方案: 提取 silence duration 分布,与真实对话的 silence 分布做 KL 散度

#### 层级 3: 整体感知 (高阶)
- **对话 MOS**: 让评估者听完整段对话后打分 (非逐句)
  - 维度: 自然度 / 拟人度 / 沉浸感
- **A/B 偏好测试**: 相同脚本,对比系统 vs 真人录音
- **LALM-as-Judge**: 用 Gemini/GPT-4o 等多模态模型做自动对话质量评估
  - 参考 EmergentTTS-Eval 的 LALM-as-judge 方案 (Spearman 90.5%)

#### 层级 4: Reward Model (闭环)
- 训练对话级 GRM,输入整段对话,输出多维评分
- 可用于 post-training 的 reward signal
- 参考 SpeechJudge (字节) 和 UniSRM 的 RCR-GRPO 训练方法

### 3.5 评估基础设施建议

| 组件 | 现状 | 建议 |
|------|------|------|
| **Benchmark 数据集** | PodEval/SwanBench 覆盖播客场景但粒度不够 | 构建 100+ 段多场景对话测试集 (闲聊/讲解/讨论/情感对话),比 PodEval 更细粒度 |
| **自动指标** | 仅 cpWER/cpSIM | 开发 prosody coherence / emotion trajectory / turn-timing 自动指标 |
| **人工评估协议** | 各家自定义 | 定义标准化的对话 MOS 评估流程 (段落级, 非句级) |
| **Reward Model** | 无对话级 RM | 收集对话级偏好数据,训练对话 GRM |

## 七、VoiceAgent 落地路径

### 7.1 VoiceAgent 与播客生成的关系

VoiceAgent 是长上下文对话语音生成的一个受约束子集:

| 维度 | 播客生成 | VoiceAgent |
|------|---------|------------|
| 说话人数 | N (2-8) | 2 (固定: 用户+Agent) |
| 用户侧音频 | 模型生成 | 真实输入 |
| 延迟要求 | 离线,无要求 | 实时,首包 <500ms |
| 上下文长度 | 分钟~小时 | 通常几轮,分钟级 |
| 流式 | 不需要 | 必须 |

VoiceAgent 在说话人数和上下文长度上更简单,但在延迟和流式上有硬约束。核心技术诉求相同: 根据对话历史生成上下文适配的语音。

### 7.2 零样本克隆的风格锚定问题

在 VoiceAgent 落地路径中,存在一个架构层面的内在矛盾:

当前零样本克隆通过参考音频 (prompt) 提取说话人特征,但实际上提取的不只是音色 — **也包含了风格基调**。如果 prompt 是平淡朗读风格,后续生成的所有语音都会被拉向"平淡"基调,即使 style tag 指定了不同风格。

```
需要一致的音色 → 固定 prompt → prompt 锁定风格基调
需要灵活的风格 → 风格随上下文变 → 与 prompt 基调冲突
```

**影响**: 即使上下文推断完美、style tag 完全正确,prompt 的风格锚定效应可能让实际控制力大打折扣。这是 L1/L2 路径能走多远的天花板。

**可能的解法方向**:

| 方案 | 做法 | 难度 |
|------|------|------|
| 风格中性 prompt | 降低 prompt 风格锚定,给 tag 更大空间 | 低,可能牺牲音色自然度 |
| 多 prompt 切换 | 同一人的不同风格录音,按场景切换 | 中,需多条参考音频 |
| 音色-风格解耦 | 架构层面分离 timbre/style 提取 (类似 NS3 四维分解) | 高,需改模型 |
| 弱化 prompt 影响 | 训练时随机化 prompt 风格,让模型不依赖 prompt 风格 | 中,需重训 |

**前置验证 (Step 0)**: 在做任何上下文注入之前,先验证现有 Instruct 能力在 VoiceAgent 场景下的实际控制力 — 选典型场景 (投诉/问答/闲聊),用现有 tag 生成,评估 prompt 风格锚定有多严重、tag 实际控制力有多大。这个前提不验证,后续路径选择都是悬空的。

### 7.3 当前管线的上下文断层

当前 VoiceAgent 主流管线中,TTS 是无状态的:

```
用户语音 → ASR → LLM (理解意图+生成回复文本) → TTS (只拿到当前一句文本) → 回复语音
                                                    ↑
                                              上下文在这里断掉
```

LLM 已经理解了完整对话上下文 (用户情绪、追问意图、对话节奏),但这些理解到了 TTS 这一步全部丢失 — TTS 只收到一句纯文本,用默认语气朗读。

### 7.4 渐进式上下文注入路径

| 层级 | 做法 | TTS 收到什么 | 改动量 | 评估重点 |
|------|------|------------|--------|---------|
| **L0** (现状) | LLM → 纯文本 → TTS | `"好的,我帮您查一下"` | — | 单句 MOS/WER |
| **L1** (最小改动) | LLM 在文本中附带 style tag | `[emotion=gentle][speed=slow] 好的,我帮您查一下` | 只改 LLM prompt,TTS 用现有 Instruct | style tag 执行准确率 + 上下文适配度 |
| **L2** (上下文传递) | LLM 输出上下文摘要 → Instruct TTS | `[context=用户刚投诉,语气焦急] 好的,我帮您查一下` | LLM prompt + TTS 支持 context description | context description 覆盖度 + 合成适配度 |
| **L3** (音频上下文) | 前几轮 text+audio token 一起喂给 TTS | text-speech interleaved 序列 | 需要重训 TTS,对话数据 | 跨句韵律连贯性 + 情感轨迹 |
| **L4** (端到端) | LLM 直接输出语音 token | Qwen3-TTS / Kimi-Audio 路线 | 换架构 | 全链路对话自然度 |

**实现路径与评估能力必须同步推进**:

| 实现层级 | 表现力阶段 | 可用评估 |
|---------|----------|---------|
| **L0→L1** | Phase 1: 5-8 个高频离散风格 (开心/安慰/客服/笑声...) | SER 分类器判断风格是否执行正确 + 上下文匹配率 |
| **L1→L2** | Phase 2: 自然语言描述 ("温和但坚定地") | LALM-as-Judge + CAWR 对比偏好 |
| **L3+** | Phase 3: 隐式上下文推断 | 对话级 RM + 人类偏好数据 |

**L1 是当前最务实的起点**: 上下文理解让 LLM 干 (它本来就擅长),TTS 用现有 Instruct 执行离散风格。评估也最容易 — 分类器可直接判断风格是否被正确合成。Phase 1 做实后自然知道哪些维度值得扩展。

**L2 → L3 的跨越需要**: 对话训练数据 + 架构支持长上下文输入 + 解决流式推理延迟。L1/L2 阶段积累的经验 (哪些上下文信号对自然度影响最大、什么粒度的控制足够) 直接指导 L3 的设计。

### 7.5 VoiceAgent 场景的评估问题

当前 VoiceAgent 评估的现状与缺失:

**已有评估** (各模块独立):
- ASR 准确率 (WER)
- LLM 响应质量 (相关性、正确性)
- TTS 单句质量 (MOS、WER)
- 端到端延迟 (TTFB、RTF)

**缺失的维度** — 没有人在评估"TTS 说得对不对":

| # | 缺失维度 | 定义 | 为什么重要 |
|---|---------|------|-----------|
| 1 | **上下文-语气匹配度** | Agent 的语气/情感是否与对话上下文匹配 | 用户在投诉,Agent 用欢快语气回应 = 灾难 |
| 2 | **跨轮一致性** | Agent 在多轮对话中音色/风格是否稳定 | 每轮换一种说话风格 = 不像同一个人 |
| 3 | **渐进退化** | 长对话中 TTS 质量是否随轮次下降 | 前几轮正常,后面越来越机械 |
| 4 | **上下文改善度** | 加入上下文后比无上下文好多少 | 验证 L1→L2→L3 每步是否真的有收益 |
| 5 | **指令执行准确率** | Instruct tag 是否被正确执行 | L1/L2 的前提: TTS 要能正确执行指令 |

**评估方案建议**:

#### 对比评估 (验证每个层级的收益)

构建 VoiceAgent 对话测试集,同一段对话分别用 L0/L1/L2 生成 Agent 语音,做 A/B 偏好测试:
- 相同文本回复,L0 (无上下文) vs L1 (style tag) vs L2 (context description)
- 评估维度: 自然度 / 上下文适配度 / 整体对话体验
- 预期: L0→L1 有明显提升 (情感匹配),L1→L2 提升较小但在复杂场景更鲁棒

#### 场景化测试集

| 场景 | 上下文信号 | 期望的 Agent 语气 | 测试要点 |
|------|----------|-------------------|---------|
| 用户投诉 | 语气急促/不满 | 安抚、温和、坚定 | L0 会用默认语气,L1+ 应该切换 |
| 知识问答 | 追问细节 | 耐心、清晰、讲解式 | 语速放慢,重点强调 |
| 闲聊 | 轻松氛围 | 活泼、自然 | 不应过于正式 |
| 情绪转折 | 从投诉到满意 | 从安抚渐变到轻松 | L0 无法处理渐变,L2+ 应该能 |
| 长对话 (10+ 轮) | 累积上下文 | 持续稳定 | 测试是否退化 |

#### 自动评估 (三条路线)

**路线 1: 违和检测 + 韵律偏移 — 不问"对不对",问"有没有明显不对"**

VoiceAgent 需要的是对话式语气 (微妙的连续调整),而非演绎式情感 (离散类别)。现有 SER 分类器对后者有效,对前者几乎无效。因此不做分类匹配,而是:

**(a) 违和检测**: 检测明显不合适的语气 — 投诉场景下欢快语气、严肃话题下轻浮语气。这些 case 即使现有 SER 也能捕捉,因为违和程度足够大。

**(b) 韵律偏移合理性**: 不判断情感类别,测量 F0/语速/能量是否随上下文合理变化:
```
用户语速加快 (急促) → Agent 语速应放慢 (安抚)  → 测量: 是否发生了方向性偏移
用户语调上扬 (追问) → Agent 应有解释性韵律    → 测量: F0 range 是否收敛
```
- 优势: 不依赖分类器,纯信号处理
- 局限: 只能检测"是否有变化",不能判断变化是否恰当

**路线 2: LALM-as-Judge — 多模态大模型判定**

最强的自动评估方案,直接让多模态 LLM 听完整段对话后判断:

```
输入: 完整对话音频 (用户真实语音 + Agent 合成语音)
Prompt: "听完这段对话,Agent 最后一句回复的语气/情感/语速是否与对话上下文匹配?
        请从以下维度 1-5 打分: (1) 情感适配度 (2) 语速适配度 (3) 整体自然度,并解释理由。"
输出: 多维评分 + 可解释理由
```

- EmergentTTS-Eval 在单句 TTS 上验证了 LALM-as-Judge 与人类评分 Spearman 相关性达 90.5%
- 对话上下文场景的 LALM-as-Judge 尚无人验证 — **这本身是一个研究机会**
- 优势: 多维度、可解释、不需要训练专用模型
- 局限: 依赖 LALM 能力,推理成本较高,需做人类相关性验证

**路线 3: Context-Aware Win Rate (CAWR) — 对比胜率**

最直接验证改进有效性的指标:

```
同一段对话的同一句 Agent 回复:
  - L0 生成 (无上下文)  → 语音 A
  - L1/L2 生成 (有上下文) → 语音 B
  → LALM 或 SER pipeline 判断哪个更匹配上下文 → 胜率
```

- 不需要绝对分数,只需要相对偏好,评估更稳定
- 如果 L1 稳定胜过 L0 (胜率 >60%),就说明 style tag 注入有效
- 可用 LALM-as-Judge 或 CEA pipeline 做自动判定
- 优势: 直接回答"加入上下文是否有用",最接近产品决策需求

**辅助指标:**

- **指令执行率 (IFA)**: 对 L1/L2 生成的语音做情感识别,验证与 style tag / context description 的一致性 — 衡量 TTS 是否正确执行了上下文推断出的指令
- **跨轮 SIM**: 计算 Agent 在对话全程各轮的 speaker similarity,检测音色漂移
- **韵律离散度**: 对比 L0 vs L1/L2 的 F0/energy 方差 — L0 倾向于所有句子韵律雷同 (默认语气),L1/L2 应有更大的合理方差
