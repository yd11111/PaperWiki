# Phase Review — P1

## 1. 阶段总览
- 阶段名称：P1 Core Engine
- 阶段目标：精读 ingest pipeline 可靠工作——丢 PDF → 出 deep note → 实体页更新 → local lint 通过
- 对应 spec：第七章(pipeline)、第九章(审核机制)、第十章(lint 基础部分)
- 前置阶段：P0
- 核心问题：精读 pipeline 能否稳定产出符合模板的高质量笔记并正确更新实体页
- 非目标：不做 KB 检索;不做每日推荐;不做 MOC 覆盖检查;不做高级 lint

## 2. 可实现性审查
### 输入
- 结论：明确
- 问题：输入是 PDF 文件或 URL。paper-reader skill 是已有能力,P1 是配置它按 AGENTS.md 规则输出。

### 输出
- 结论：明确
- 问题：产出物清晰:论文笔记(tier:deep) + 实体页(status:pending-review) + log 条目 + git commit。每项都有 frontmatter 可验。

### 闭环
- 结论：成立
- 问题：PDF → deep note → entity pages → lint → commit。独立可用——即使后续阶段不做,P1 本身就是一个可用的"论文精读 + 概念整理"工具。

### 复杂度
- 结论：中偏高
- 问题：
  - 精读笔记的内容质量(机制理解 vs 摘要)依赖 agent 能力,不是规则能完全保证的
  - "追加 vs 实质"判定在实际中可能出现模糊边界
  - 这是整个系统中第一次让 agent 做复杂内容生成,质量方差是真实风险
- 最可能导致实现失控的点：agent 第一次生成的 deep note 质量不达标,需要反复调整 prompt/规则

### MVP / 简化路径
- 结论：有
- 建议的 MVP 版本：
  - MVP: 只做 deep note 生成 + frontmatter 正确,不做反向更新。手动创建实体页。
  - V1: 加反向更新(只做追加)
  - V2: 加实质修改判定 + local lint
  - Plan 当前是直接做 V2。建议如果反向更新有问题,先退到 V1。

### 小样本试运行
- 结论：适合
- 建议样本：3 篇论文(plan 已定义),1 篇已知论文(验证准确性)+ 1 篇共享概念(验证 append)+ 1 篇新领域(验证新实体创建)

### 可实现性总评
- 结论：**中高**
- 阻塞项：无硬阻塞。主风险是内容质量,但有 draft→reviewed 人工审核兜底。
- 建议：第一篇用你已读过的论文,便于验证正确性。

## 3. 正确性审查
### 系统职责对齐
- 结论：对齐
- 问题：P1 主要服务"懂"(精读笔记)和"连"(实体页更新)。不损害"筛"。

### 四条底线
- 结论：符合
- 最薄弱项：**可溯源**。claim 标注依赖 agent 执行纪律。plan 有 grep 检查 marker 存在性,但不能验证标注正确性。人工 review(draft→reviewed)是唯一真正保障。

### 六条原则
- 结论：符合
- 风险点：
  - 原则 5(默认不升级):P1 不涉及升级,安全
  - 原则 4(失败降级):Task 8 专门测试,覆盖
  - 原则 1(可信层):新实体页 status=pending-review,正确

### 审阅必改项覆盖
- 结论：覆盖
- 遗漏项：
  - **D. 审核节奏** — Task 9 有 batch review,但没有定义"以后每周什么时候做"。Plan 不是运营手册,这个放在 P4 lint 周报中触发更自然。可接受。

### 正确性总评
- 结论：**高**
- 建议：无

## 4. 风险审查
- 复杂度风险：**中**。agent 需要同时做:读 PDF + 按模板生成 + 正确填 frontmatter + 判断实体是否存在 + 做追加更新。步骤多。
- 判定风险：**中**。"追加 vs 实质"在实际中有模糊地带(如:往"在 TTS 中的应用"节追加一段新应用——这算追加还是实质?)。Plan 的形式化规则("只动列表/表格末尾 = 追加")覆盖了大部分情况,但不是 100%。
- 数据风险：**低**。3 篇论文即可验证。
- 使用风险：**低**。审核 3 篇笔记 + 几个实体页,30-60 分钟。
- 风险总评：**可接受。** 主风险是内容质量和追加/实质边界,但都有人工审核兜底。

## 5. 验收审查
### 功能验收
- ≥ 3 deep notes (grep tier:deep) ✓
- ≥ 1 reviewed note ✓
- ≥ 5 entity pages ✓
- ≥ 1 confirmed entity ✓
- 0 unaccounted dead links ✓
- ≥ 1 failure handled (skip/ingest in log) ✓
- 评价：**中高**。数量+结构验收充分。内容质量仍依赖人工判断(不可避免)。

### 原则验收
- pending-review 正确(新实体页不进可信层) — Task 5/6 验证
- 失败降级 — Task 8 验证
- 默认不升级 — P1 不涉及升级
- 评价：**高**

### 失败验收
- Task 8: PDF 解析失败 → 不 commit + 写 log
- 评价：**中**。只覆盖了 1 种失败。其他可能失败(如 frontmatter 生成不全、实体页写入失败)未显式测试。但"不完美但可运行"哲学允许这些在 P4 lint 中发现。

### 测试场景
- 正常：已知论文 → 验证准确性(Task 5)
- 边界：共享概念 → 验证 append 不改 status(Task 6)
- 失败：坏 PDF → 验证降级(Task 8)
- 评价：**够用**。覆盖了最关键路径。

### Done Definition
- Plan 定义了 7 项客观验收 + tag
- 评价：**清晰可执行**

## 6. 结论
- 分类结论：**可直接进入实现**
- 必改项：无
- 可选优化项：
  1. 可以在 Task 6 中增加一个更精确的 diff 检查(git show 对比前后概念页变化,确认只有 key_papers 变了)
  2. 可以增加一个"frontmatter 生成不全"的失败测试(给 agent 一个信息极少的输入)
- 一句话判断：P1 是系统核心,复杂度中等,验收标准清晰,风险有人工审核兜底,可以开始。

### 红线检查
- [x] 没有绕过人工确认把内容放进可信层(新实体 pending-review,新笔记 draft)
- [x] 没有把未来阶段的复杂度提前塞进来(无 KB 检索,无 MOC)
- [x] 没有让失败阻断整个主流程(Task 8 验证)
- [x] 没有让自动化替代本该由你做的认知决策(升级由你触发,确认由你做)
- [x] 没有让系统主视图退化为"论文列表堆积"(产出实体页,不只是笔记)

# Phase Review — P3

## 1. 阶段总览
- 阶段名称：P3 Compound Interest
- 阶段目标：精读/复现笔记自动获得 KB 背景;复现级模板验证;alias 反馈回路验证
- 对应 spec：第八章(KB 检索)、第七章(复现 pipeline)
- 前置阶段：P1(需要 ≥ 5 confirmed 实体页)
- 核心问题：KB 检索能否为新论文提供有价值的定位背景,且成本可控
- 非目标：不做高级 lint;不做 MOC;不优化推荐质量

## 2. 可实现性审查
### 输入
- 结论：明确
- 问题：输入是新论文 + 已有 confirmed 实体页。前提是 P1 产出了足够的 confirmed 页面。如果 P1 只确认了 2 个概念页,P3 效果会很弱。

### 输出
- 结论：明确
- 问题：笔记中的 KB 背景节 + kb_context_sources 字段 + log [kb/search] 条目。可验。

### 闭环
- 结论：成立
- 问题：新论文 → KB 检索 → 找到实体页 → 生成定位 → 写入笔记。闭环。且 alias 反馈回路(Task 17)形成"越用越准"的正向循环。

### 复杂度
- 结论：**中高**
- 问题：
  - KB 检索的三条件匹配 + 排序 + 筛选,逻辑上清楚但实现时 agent 需要执行多步搜索
  - 降级场景有 3 种(无匹配/只有 pending/过时),每种需要不同标注
  - 复现级笔记的深度要求高(模块细节、loss 公式、训练配置),agent 能否稳定产出此深度有不确定性
- 最可能导致实现失控的点：KB 检索召回率不足(alias 覆盖不够),导致 KB 背景节总是"未找到"。

### MVP / 简化路径
- 结论：有
- 建议的 MVP 版本：
  - MVP: 只做条件 3(frontmatter 直接引用)的精确匹配,不做 tag 模糊匹配。召回率低但零误差。
  - V1: 加条件 1(title/alias 匹配)
  - V2: 加条件 2(tags 交集)
