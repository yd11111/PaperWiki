# PaperWiki 使用手册

## 1. 系统概览

PaperWiki 是一个以 TTS/语音合成为核心的个人知识库,由 Claude Code 辅助维护。你通过自然语言下达指令,Agent 负责论文阅读、笔记生成、概念页维护、审阅检查和系统检查。知识库的主视图是实体页(概念/模型/数据集) + MOC 导航,论文笔记是输入端,实体页是沉淀端。核心哲学:允许不完美但可运行。

## 2. 日常操作速查表

| 你想做什么 | 说什么 | 系统会做什么 | 产出在哪 |
|---|---|---|---|
| 精读一篇论文 | "读一下这篇 [URL/PDF路径]" | KB 检索 → 生成草稿 → **自动审阅** → 反向更新 → 自动检查 | `论文笔记/` + `_review/` |
| 从 inbox 处理 | "处理一下 inbox" | 逐条检视 `_inbox/` 条目,询问你要精读/快看/跳过 | 视选择而定,处理后删除 |
| 每日论文推荐 | "今日论文推荐" | 抓取当天 arXiv 论文 → 打分筛选 → 生成 card | `DailyPapers/` + `论文笔记/` |
| 选读(升级为加强卡片) | "快速看一下 [[某篇]]" | 在已有 card 基础上扩展为 enhanced-card | 原文件原地升级 |
| 指定复现级阅读 | "复现分析 [URL/PDF]" | KB 检索 → 生成 repro 笔记 → **审阅** → 反向更新 | `论文笔记/` + `_review/` |
| 用某篇论文重写概念页 | "用 [[论文]] 重写 [[概念]]" | 以指定论文为权威来源,重写概念页 | `概念库/`, status → pending-review |
| 搜索补充概念页 | "搜索补充一下 [[概念]]" | Playwright 搜索 → 补充概念页 | `概念库/`, status → pending-review |
| 审阅一篇笔记 | "审阅这篇笔记 [[论文]]" | 对照 checklist 检查 5 维度 × 10 问题类型 | `_review/xxx-review.yml` |
| 批量审阅 | "批量审阅所有笔记" | 审阅所有未审阅的 deep/repro 笔记 | `_review/` 多个报告 |
| 系统检查 | "系统检查" 或 "检查一下系统" | 按四条底线(可导航/可溯源/不腐烂/完整性)全面扫描 vault | `_lint/` 报告 |
| 深度分析 | "深度分析" | 语义级检查(矛盾/过期SOTA/缺失关联),成本高 | `_lint/` 报告 |
| 确认实体页 | "batch review" | 列出 pending-review 实体页,逐个确认 | status → confirmed |
| 收一篇到 inbox | "收一下 [URL],因为 [原因]" | 在 `_inbox/` 创建最小条目 | `_inbox/` |
| 合并概念 | "把 [[A]] 合并到 [[B]]" | 内容迁移 + 全局替换引用 + 删除旧文件 | `概念库/` B 页更新 |

## 3. 笔记层级说明

| 层级 | 什么时候用 | 深度 | 能否被引用 |
|---|---|---|---|
| **card** | 每日推荐/扫一眼 | 标题+一句话+标签 | 不能 |
| **enhanced-card** | 想快速了解核心方法 | 摘要+方法+结果 | 不能 |
| **deep** | 认真精读 | 完整机制分析+实验+KB 背景+**自动审阅** | 审核后可以 |
| **repro** | 要复现/深度理解 | 代码级分析+复现要点+**自动审阅** | 审核后可以 |

升级只能由你触发。Agent 永远不会自作主张升级。

## 4. 精读完整流程 (7 步)

```
① 读原文 PDF (pdftotext 优先)
② KB 检索 (搜索 confirmed 实体页,生成背景)
③ 生成笔记草稿 (含速查卡片 + KB 背景 + [论文原文]/[agent 解读] 标注)
④ 审阅 (反向更新前,检查 5 维度 × 10 问题类型)
⑤ Git commit 草稿 + 审阅报告
⑥ 反向更新 (仅审阅通过后: 追加已有页 / 创建新实体页)
⑦ 自动检查 + Git commit + log (frontmatter/MOC/wikilink 检查,有遗漏当场补)
```

审阅在反向更新之前——如果笔记有错误,不会污染概念页。

---

## 5. 审阅模块

### 自动审阅 (每次精读后)

每次生成 deep/repro 笔记后自动触发。检查 5 个维度:

| 维度 | 检查什么 |
|---|---|
| 可理解性 | "方法"节是解释 WHY 还是罗列 WHAT |
| 可溯源性 | 数字 claim 有没有 [§]/[Table] 标注,覆盖率多少 |
| 严谨性 | 指标名对不对,"SOTA/唯一" 等断言有没有证据 |
| 可导航性 | 概念挂接完整吗,速查卡片 5 字段有实质内容吗 |
| 知识库安全 | 新建概念满足准入规则吗,反向更新内容有事实错误吗 |

**审阅结论:**
- **pass** → 直接反向更新
- **pass-with-fixes** → 有 medium 问题,建议修正,可放行
- **revise** → 有 high 问题,必须修正后才能反向更新
- **reject-as-deep** → 质量不达标,建议降为 enhanced-card

**产出:** `_review/xxx-review.yml` (结构化) + 笔记末尾 `[!review]` callout (人类可读)

### 手动审阅

说 "审阅这篇笔记 [[论文名]]" 可以对任意已有笔记做审阅。

### 跨篇模式分析

每 5-10 篇后说 "分析审阅模式",系统统计高频问题 → 判断根因 → 产出系统升级建议。

## 6. 知识库怎么帮你

读第 N+1 篇论文时,系统自动检索 confirmed 实体页,注入"KB 背景"节:
- 谱系定位: 这篇在已有认知里什么位置
- 已有认知: 库里对相关概念已知什么
- 创新判断: 相对已知方法,新在哪

读得越多 → 概念页越厚 → 下一篇背景越丰富 → 复利。

---

## 7. 审核节奏建议

| 时机 | 做什么 | 耗时 |
|---|---|---|
| 每精读 3-5 篇后 | "batch review" 确认实体页 | 5-10 min |
| 每周一次 | 说 "系统检查" 看健康报告 | 5 min |
| 精读后看一眼 | 笔记末尾的 `[!review]` callout,只看 high/medium 问题 | 1-2 min |
| backlog 告警时 | pending-review >= 10 或 draft deep >= 5 | 按需 |

审核时重点看审阅 callout 标出的问题,不必逐字校对。不是强制节奏。

## 8. 概念页成熟流程

三条成长路径:
1. **自动积累**: 每次精读,Agent 追加 key_papers + 贡献描述(不改 status)
2. **指定重写**: "用 [[论文]] 重写 [[概念]]" → 以论文为权威重写(→ pending-review)
3. **搜索补充**: "搜索补充 [[概念]]" → Playwright 搜索补充(→ pending-review)

溯源提醒: key_papers >= 3 但 origin_paper 空 → 系统检查会提示找原始论文。

概念去重: 系统检查会扫描 title/aliases 重叠,提示 merge 候选。merge 时不留 redirect,直接替换引用+删旧文件。

## 10. 注意事项

- **每日推荐只收当天论文** — HuggingFace trending ≠ 当天,系统过滤
- **Card/enhanced-card 永远不可信** — 只有 reviewed deep/repro 和 confirmed 实体页才是可信层
- **审阅在反向更新前** — 有 high 问题的笔记不会污染概念页
- **[论文原文]/[agent 解读]** — 精读笔记的"方法"节须标注解释来源
- **允许不完美** — 死链/孤儿/pending 积压是正常状态
- **网络操作用 Playwright** — WebFetch/WebSearch 不稳定
- **升级需要你说** — Agent 不自动升级 tier
- **Append 不改 status** — 往 confirmed 页追加不打回 pending-review
- **概念准入规则** — 新建概念须满足 ≥2 条: 多篇引用 / 前置知识 / 连接论文
- **合并不留 redirect** — grep 替换所有引用 + 旧名进 aliases + 删旧文件
